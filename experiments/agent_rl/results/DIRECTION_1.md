### 一次重要的自我纠错

初版报告「循环率 87.4%、时间视界 3.2 步」是**错的**：

```python
# 错误：只看工具名
tools = ["bash", "bash", "bash"]   # 判为循环
# 实际：bash(ls) → bash(find) → bash(cat) 是三次不同探索
```

修正为「工具名 + 关键参数」后：**循环率 87.4% → 1.3%，时间视界 3.2 → 10.1**。

**教训**：指标定义错了，后面所有分析都是错的。任何指标先在 5–10 条样例上人工验证。

详见 `results/CORRECTION.md`。

## 三、稠密奖励

### 四个可验证来源

| 来源 | 规则 | 分值 |
| --- | --- | --- |
| 测试进展 | 通过数 a → b | +(b−a)/total |
| 回归惩罚 | 原本通过的变失败 | −0.3/个 |
| 目标文件命中 | 改对文件 | +0.2 |
| 无效动作 | 重复动作 | −0.02 |

无测试快照时按动作信息价值分级：`edit/write` 0.4 > `bash+pytest` 0.1 > 探索 0.05。

### 实测

| 指标 | 稀疏奖励 | **稠密奖励** |
| --- | --- | --- |
| 非零信号数 | 1 个 | **9.3 个** |
| 信号密度 | — | **84.7%** |
| 平均分 | 1.0（全同） | 0.825 |

### 在线版设计（待实测）

在沙盒里每步跑一次 pytest，拿到真实 `(passed, failed)`：

step1 edit  gain=0.00  total=0.00   ← 改了但测试还不过

## 四、循环打断器

| 指标 | 值 |
| --- | --- |
| 触发率 | **0.9%**（5/531） |
| 终止率 | 0% |
| 误伤分析 | 5 条触发中，5 条都是**成功轨迹**的验证型重复 |

**结论**：打断器不会误伤正常探索，只在真退化时做护栏。

## 五、与方向二的关系

方向一的稠密奖励**直接用于方向二的 GRPO**：

```
GRPO 的优势计算：A_i = (r_i − mean(r_group)) / std(r_group)
```

| 场景 | 稀疏奖励 | 稠密奖励 |
| --- | --- | --- |
| 全部成功 | 全 1.0，std=0，**无梯度** | 0.6–1.1 波动，**有梯度** |
| 全部失败 | 全 0.0，**无梯度** | 过程分可区分「接近成功」与「毫无方向」 |

**这是让 GRPO 在饱和任务上也能训练的关键，也是方向一与方向二的交汇点。**
