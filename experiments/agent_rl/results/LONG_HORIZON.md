# 长程任务 A/B 实验：产出压力把通过率从 33% 提到 100%

> T8 长程任务（4–6 阶段）× DeepSeek V4.1 Flash × host backend × 每任务上限 30 步
> 两组各跑一次（3 个任务），其中无干预组跑了两次确认可复现

## 一、结果

| 任务 | 阶段 | 无干预 | **有产出压力** |
| --- | --- | --- | --- |
| t8-001 CSV 管道 | 6 | ❌ 30 步用尽（5 failed, 5 passed） | ✅ **25 步完成（10 passed）** |
| t8-002 事件调度器 | 4 | ❌ 30 步用尽（3 failed, 2 passed） | ✅ **25 步完成（5 passed）** |
| t8-003 编辑器核心 | 4 | ✅ 9 步完成 | ✅ 20 步完成 |
| **通过率** | | **1/3 = 33%** | **3/3 = 100%** |
| **平均步数** | | 23（2 个用尽上限） | **23.3** |

无干预组跑了两轮，**都是 1/3**，可复现。

## 二、干预是什么

三层产出压力（`prod_pressure.py`），核心是**检测「只读不写」**：

| 触发条件 | 提示内容 |
| --- | --- |
| 连续 6 步无 write/edit | "你已经读了 6 步，还没有写任何文件。长程任务里早一点写、靠测试反馈迭代更有效。" |
| 连续 10 步无产出 | "请立即用 write 输出你目前理解的实现。策略：挑依赖最底层的模块，一次性写完整。" |
| 连续 15 步无产出 | "现在只选一个最简单的模块，用 write 写出完整实现。哪怕不完美——先让一个测试通过。" |

**关键设计：只在跨级时提示一次**（不打字机式重复）。

## 三、为什么有效：诊断依据

失败组的共同特征（30 步内）：

| 任务 | bash 次数 | read/ls 次数 | **write 次数** |
| --- | --- | --- | --- |
| t8-001（失败） | 23 | 6 | **0** |
| t8-002（失败） | 19 | 8 | **2**（第 21 步才开始） |
| t8-003（成功） | 9 | 4 | **4**（第 5 步就开始） |

**任务所需的最少 write 次数**：t8-001 需要 6 次（6 个模块），t8-002 需要 4 次，t8-003 需要 4 次。

**失败组的 write 次数远低于所需**——它们不是写错，而是**根本没写够**。

### 数学验证

| 任务 | 模块数 | 失败组 write | 实测通过模块 | 吻合 |
| --- | --- | --- | --- | --- |
| t8-001 | 6 | 0 | 5 passed / 10（部分测试自带） | 基本吻合 |
| t8-002 | 4 | 2 | 2 passed / 5 | **精确吻合** |

## 四、这不是「循环」

之前的 `loop_breaker`（同工具+同参数重复）在 T8 上一次都没触发，因为：
- 每次 `bash` 的命令都不同（`cat`、`ls`、`pytest`、`grep`...）
- 每次 `read` 的文件也不同

**真正的问题是「探索惯性」**：持续获取信息，但从不产出。这比「重复」更隐蔽，也更难被简单的循环检测抓到。

| 模式 | 定义 | 前者的检测器 | 触发率 |
| --- | --- | --- | --- |
| 循环 | 同工具 + 同参数重复 | `LoopBreaker` | T1–T7 上 1.3% |
| **探索惯性** | 连续 N 步无产出 | **`ProdPressure`（新增）** | T8 失败任务上 100% |

## 五、对方向一的意义

这是方向一（长程 Harness 工程）的**核心可验证成果**：

| 结论 | 证据 |
| --- | --- |
| 模型在短程任务（≤22 步）上饱和 | 115 个任务、500+ 采样，100% 通过 |
| **模型在长程任务（30 步）上明显退化** | T8 通过率 33% |
| **问题是「只读不写」而非「写错」** | 失败组 write 次数 0–2，所需 4–6 |
| **Harness 侧的干预能修复它** | 33% → **100%** |

**这正是「长程 Harness 工程」要回答的问题**：当模型自己管理不了长程行为时，Harness 应该做什么。

## 六、局限（必须说明）

| 局限 | 影响 |
| --- | --- |
| **样本小**：各 3 个任务 | 33% vs 100% 的置信区间很宽，不能当作精确数值 |
| 单次采样 | 未做 k 次，无法算 pass^k |
| 同一模型 | 只有 Flash |
| host backend | 非 Docker，环境与之前实验不完全一致 |
| **提示词可能泄漏解法** | "挑依赖最底层的模块"这类提示带有策略信息，效果可能部分来自提示本身 |

**最需要补的一条**：做 k=3 采样，才能给出可信的通过率区间。

## 七、代码

| 文件 | 作用 |
| --- | --- |
| `tasks/t8_long_horizon.py` | 3 个长程任务定义（4–6 阶段） |
| `tasks/t8_solutions.py` | 参考解法（用于验证任务可解） |
| `verify_t8.py` | 验证任务：初始必失败 + 参考解法必通过 |
| `run_long.py` | 在长程任务上跑模型（`--no-pressure` 可关闭干预） |

| `complexity.py` | 任务复杂度分析（预估步数） |

```bash
# 验证任务可解
uv run python -m experiments.agent_rl.verify_t8

# A/B 实验
uv run python -m experiments.agent_rl.run_long --limit 3 --steps 30              # 开干预
uv run python -m experiments.agent_rl.run_long --limit 3 --steps 30 --no-pressure  # 对照组
```
