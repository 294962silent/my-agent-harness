## 二、可验证奖励的两层设计

### 为什么分层

TRL 的 `GRPOTrainer` 只接受 `completions -> list[float]` 的同步奖励函数，
但 agent 任务需要**执行**才能知道结果，而训练循环里不能跑 Docker。

因此拆成两层：

| 层 | 何时算 | 用什么 | 是否需要执行 |
| --- | --- | --- | --- |
| **第 1 层：结构奖励** | 训练循环里实时 | `structure_reward()` | ❌ 不需要 |
| **第 2 层：执行奖励** | rollout 阶段预先算 | 沙盒 + pytest | ✅ 需要 |

实际训练流程：

```
阶段 A：用 harness 跑 rollout
   prompt → 模型输出 → 沙盒执行 → (成功?, 稠密分)
   把 (prompt, completion, 结构分, 稠密分, 成功) 落盘

阶段 B：把落盘数据当数据集训练
   GRPOTrainer 的 reward_fn 直接读缓存值
```

### 第 1 层：结构奖励（已实现并验证）

| 检查项 | 分值 |
| --- | --- |
| 有合法 JSON 动作 | +0.4 |
| 动作名在白名单 | +0.3 |
| 参数完整（path/command/oldText+newText） | +0.2 |
| 纯 JSON（无多余文字） | +0.15 |
| markdown 代码块包裹 | −0.1 |
| 过长（>1000 字符） | −0.15 |
| 无 JSON | −0.5 |
| 空输出 | −1.0 |

**自测结果**：

| 输入 | 分数 | 判断 |
| --- | --- | --- |
| 完美 JSON 动作 | **+1.00** | ✅ |
| 带 markdown 包裹 | +0.80 | ✅ |
| 带 `<think>` 块 | +0.90 | ✅ |
| 纯文字回答 | **−0.50** | ✅ |
| 未知工具名 | +0.55 | ✅ |
| 空输出 | **−1.00** | ✅ |

### 第 2 层：执行奖励的组合

```python
total = 0.3 * structure + 0.3 * dense_total + 0.4 * terminal
```

| 场景 | 结构分 | 稠密分 | 终局 | 总分 |
| --- | --- | --- | --- | --- |
| 成功 | 0.8 | 0.6 | 1 | **0.82** |
| 失败 | 0.8 | 0.6 | 0 | **0.42** |

**差距 0.4 主要来自终局分**，结构分和稠密分提供梯度。

### 关键实现细节：JSON 解析的坑

第一版用了非贪婪正则 `\{.*?\}`，结果**所有测试都返回 −0.5**：

```
输入: {"name": "edit", "arguments": {"path": "mod.py", ...}}
非贪婪匹配到: {"name": "edit", "arguments": {"path": "mod.py"
```

**在第一个 `}` 处就截断了**，而动作 JSON 是嵌套的。

修正：用**括号配对 + 字符串转义感知**的解析器。

### 关键验证：SFT 确实学会了动作格式

| 配置 | 生成内容 |
| --- | --- |
| 原始 9B | `<think></think>{ "action": "fix_mod_py" }` ← **格式错** |
| **SFT 后** | `{"name": "edit", "arguments": {"path": "mod.py", "edits": [...]}}` ← **完全正确** |

**这是方向二最硬的一个结果**：SFT 把无法解析的输出变成了规范的 agent 动作。
