## 二、可验证奖励的两层设计

### 为什么分层

TRL 的 `GRPOTrainer` 只接受 `completions -> list[float]` 的同步奖励函数，
但 agent 任务需要**执行**才能知道结果，而训练循环里不能跑 Docker。

因此拆成两层：

| 层 | 何时算 | 用什么 | 是否需要执行 |
| --- | --- | --- | --- |
| **第 1 层：结构奖励** | 训练循环里实时 | `structure_reward()` | ❌ 不需要 |
| **第 2 层：执行奖励** | rollout 阶段预先算 | 沙盒 + pytest | ✅ 需要 |

实际训练流程：

```
阶段 A：用 harness 跑 rollout
   prompt → 模型输出 → 沙盒执行 → (成功?, 稠密分)
   把 (prompt, completion, 结构分, 稠密分, 成功) 落盘

阶段 B：把落盘数据当数据集训练
   GRPOTrainer 的 reward_fn 直接读缓存值
```

### 第 1 层：结构奖励（已实现并验证）

| 检查项 | 分值 |
| --- | --- |
| 有合法 JSON 动作 | +0.4 |
| 动作名在白名单 | +0.3 |
| 参数完整（path/command/oldText+newText） | +0.2 |
| 纯 JSON（无多余文字） | +0.15 |
| markdown 代码块包裹 | −0.1 |
| 过长（>1000 字符） | −0.15 |
| 无 JSON | −0.5 |
| 空输出 | −1.0 |

**自测结果**：

| 输入 | 分数 | 判断 |
| --- | --- | --- |
| 完美 JSON 动作 | **+1.00** | ✅ |
| 带 markdown 包裹 | +0.80 | ✅ |
| 带 `<think>` 块 | +0.90 | ✅ |
| 纯文字回答 | **−0.50** | ✅ |
| 未知工具名 | +0.55 | ✅ |
| 空输出 | **−1.00** | ✅ |

### 第 2 层：执行奖励的组合

```python
total = 0.3 * structure + 0.3 * dense_total + 0.4 * terminal
```

| 场景 | 结构分 | 稠密分 | 终局 | 总分 |
| --- | --- | --- | --- | --- |
| 成功 | 0.8 | 0.6 | 1 | **0.82** |
| 失败 | 0.8 | 0.6 | 0 | **0.42** |

**差距 0.4 主要来自终局分**，结构分和稠密分提供梯度。

### 关键实现细节：JSON 解析的坑

第一版用了非贪婪正则 `\{.*?\}`，结果**所有测试都返回 −0.5**：

```
输入: {"name": "edit", "arguments": {"path": "mod.py", ...}}
非贪婪匹配到: {"name": "edit", "arguments": {"path": "mod.py"
```

**在第一个 `}` 处就截断了**，而动作 JSON 是嵌套的。

修正：用**括号配对 + 字符串转义感知**的解析器。

### 训练过程中的关键指标

| 步 | reward mean | reward_std | frac_reward_zero_std |

## 八、训练前后 A/B 对比（Qwen3-1.7B）：失败记录

尝试在本地完成「训练前 vs 训练后」的完整对比。

### 设计

| 项 | 值 |
| --- | --- |
| 模型 | Qwen3-1.7B（4bit，LoRA r=8，3.2M 可训练参数） |
| 任务 | t8e-001、t8e-002（边界难度） |
| 步数上限 | 20 步 |
| 奖励 | 结构奖励（第 1 层） |

### 结果：训练前后都是 0/2

| 阶段 | t8e-001 | t8e-002 | 通过率 |
| --- | --- | --- | --- |
| 基线 | FAIL 20 步 | FAIL 20 步 | **0/2 (0%)** |
| 训练后 | FAIL 20 步 | FAIL 20 步 | **0/2 (0%)** |

**没有提升。**

### 为什么失败：训练配置有致命问题

| 指标 | 实测值 | 应该是什么 |
| --- | --- | --- |
| **训练样本** | **2 条** | ≥ 50 条 |
| `num_generations` | 2 | 4–8 |
| **`frac_reward_zero_std`** | **0.6 → 1.0** | < 0.3 |
| **`grad_norm`** | **多次为 0** | 稳定 > 0.1 |

**根因链**：

```
2 条样本 + num_generations=2
  → 每组的 2 个采样奖励相同
  → 组内 std = 0
  → 优势 A_i = 0
  → grad_norm = 0
  → 没有任何参数更新
```

**训练实际上什么都没学到。**

### 同时暴露的第二个问题：1.7B 不会输出 JSON

工具序列里有大量 `?`（解析失败的输出）：

```
基线 t8e-001: ? -> ls -> ? -> read -> ? -> ? -> read -> ? -> read -> read -> ? -> read
训练后 t8e-002: ? -> read -> read -> ? -> read -> ? -> read -> read -> read -> write -> ? -> ?
```

**训练后的 `?` 比例几乎没变**（12 个工具里 8 个是 `?`），进一步证明训练无效。

### 这不是模型的问题，是配置的问题

| 错误 | 正确做法 |
| --- | --- |
| 样本只有 2 条 | 用所有 10 个训练任务的 prompt（≥10 条），或扩充到 50+ |
| num_generations=2 | 至少 4，理想 8 |
| 只训练 30 步 | 100+ 步 |
| 只用结构奖励 | 结构 + 执行奖励（需要沙盒 rollout） |

### 但这次实验仍然有价值

| 收获 | 说明 |
| --- | --- |
| 确认了 1.7B 的基线 | **0/2，工具有效性仅 33%**（12 个里 4 个合法） |
| 确认了训练流程能跑通 | 30 步、214 秒、3.41 GB 显存 |
| **发现了配置陷阱** | `num_generations` 必须配足够的样本池 |
| 证明「跑完 ≠ 学到」 | loss 0.0326 看起来很好，但 grad_norm 为 0 |

### 修正后的正确配置

```python
# 数据：所有 10 个边界任务的 prompt + 每条重复采样
rows = [prompt for task in 10_tasks] * 5   # 50 条

GRPOConfig(
    num_generations=8,          # 每组 8 采样
    per_device_train_batch_size=8,
    max_steps=100,
    learning_rate=1e-5,
)
```

**关键：`num_generations` 越大，组内越可能产生奖励差异，梯度越稳定。**

### 结论

**本地 8GB 显卡无法完成有意义的 GRPO 能力提升实验**，原因：

| 限制 | 影响 |
| --- | --- |
| 显存 8GB | 1.7B 训练时 batch 只能到 2，`num_generations` 只能到 2 |
| **`num_generations=2` 无法产生组内差异** | 这是硬性限制 |
| 1.7B 本身能力不足 | 基线就不能输出合法 JSON，RL 难以从 0 学到 1 |

**需要 24GB+ 显存才能把 `num_generations` 提到 4–8，这就是为什么原本要用服务器的 32GB 显卡。**
