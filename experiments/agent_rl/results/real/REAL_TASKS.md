# 真实任务评测：superagent 融合点 1 的结果

> 灵感来自 DeepSeek 开源的 [`dsh-superagent-prototype`](https://github.com/deepseek-ai/dsh-superagent-prototype)
> （“Towards a More Autonomous Agent System”）。它监听 GitHub Issue，在独立工作区里干活并交付 PR。
>
> 我们采用它**不写代码、只借任务模型**：把真实 PR（Issue 描述 + 测试改动）变成可自动判定的评测任务。

## 一、动机

前面的合成任务实验（115 个任务、1108 次真实沙盒执行）结果是：

- flash 模型单次通过率 **100%**
- k=5 采样下 `pass^5 = pass@5 = 1.0`，`gap = 0`
- 加固难度（隐藏测试 / 干扰文件 / 噪声 / 多缺陷）**均不降低**通过率

结论是「数据饱和、无法训练」。但这是一个**合成任务**的结论——真实工作是不是也这样？

## 二、做法

```
GitHub PR（已合并）
  ├─ Issue 正文      → 任务 prompt（真实、模糊，可能不完整）
  ├─ 测试文件改动    → 判定标准
  └─ base commit     → 工作区代码快照（修改前）
```

### 采集（`collect_real.py`）

筛选条件：
- 已合并的 PR
- 同时改了 `.py` 测试和 `.py` 源码（排除 CI 配置、文档）
- 改动文件 ≤ 12，源码文件 ≤ 6（太大的 PR 不适合单次任务）
- 排除 "merge stable"、"bump version" 这类无意义提交

结果：**102 个候选任务**，覆盖 click / flask / requests / black / pip / attrs。

### 严格验证（`prepare_real.py`）

每个任务必须同时满足三条，否则丢弃：

| 校验 | 含义 | 淘汰原因 |
| --- | --- | --- |
| ① 旧代码 + 新测试 = **失败** | 任务确实有待解决的问题 | 旧代码居然通过 → 判定无效 |
| ② 输出里**没有** `ModuleNotFoundError` 等 | 不是环境缺依赖 | 缺 `installer`/`hypothesis` → 不可评测 |
| ③ 打上 PR 的真实修复后 = **通过** | 任务可达 | 真实修复也不通过 → 任务不可达 |

**102 → 21 个完全可用任务。**

淘汰分布：

| 原因 | 数量 |
| --- | --- |
| 真实修复也无法通过（只替换改动文件不够，需要完整 diff 上下文） | 约 40 |
| 环境缺依赖（pip 要 `installer`、attrs 要 `hypothesis`） | 约 36 |
| 旧代码通过（PR 只改了测试） | 5 |

## 三、结果

| 任务类型 | 任务数 | 单次通过率 | 平均步数 | 单任务耗时 |
| --- | --- | --- | --- | --- |
| **合成任务** | 115 | **100%**（500 次采样全过） | 8 | 15–25 秒 |
| **真实 PR 任务** | 21 | **0 / 2（取样）** | **89 / 95** | **12–20 分钟** |

> 真实任务只测了 2 个就停止（每个要 12–20 分钟），样本小，**结论是方向性的，不是精确比例**。

### 失败形态完全不同

合成任务失败时：改错了某一行。
真实任务失败时：**89 步里大部分在 `find` / `ls` / `grep` 地找文件**：

```
bash → bash → ls → find → bash → find → ls → bash → find → find
→ read → bash → read → find → bash → find → ls → grep → ls → ls
```

判定输出显示它最终改了地方，但**没改对**：

```
FAILED tests/test_options.py::test_missing_envvar_sequence[envvar2-...]
17 failed, 659 passed in 2.36s
```

## 四、结论

### 1. 合成任务的「饱和」不代表真实工作饱和

| | 合成任务 | 真实任务 |
| --- | --- | --- |
| 仓库规模 | 3–8 个文件 | 200+ 文件（click 2.2 MB） |
| 任务描述 | 明确点名 bug | 真实 issue，模糊且可能不完整 |
| 定位成本 | 几乎为零 | **主要失败原因** |
| 通过率 | 100% | 接近 0（小样本） |

**模型不缺「改代码」的能力，缺的是「在大仓库里找到要改什么」的能力。**

这正好呼应合成任务实验里的另一个发现：信息可得性从 100% 降到 0%（测试不可见时），
而真实任务的信息可得性天然就更低——**没有人为把测试藏起来，仓库本身就把答案埋住了**。

### 2. 这解释了为什么合成任务无法训练

合成任务的 `gap = 0`，是因为**难度不在定位环节**。真实任务的失败集中在定位，
而定位是可以被训练的能力（搜索策略、读代码顺序、利用测试反馈）。

**如果要做 Agent RL，真实任务才是有训练价值的数据源。**

### 3. 融合方式：借任务模型，不写插件

superagent 的 `Source` 是 TypeScript 插件（需要 cordis、zod、KV、CLI 契约），
接入成本高且产出（多支持一个事件源）与我们的目标（评测能力）不匹配。

我们借的是它的**领域模型**：

| superagent 概念 | 我们的对应 |
| --- | --- |
| Issue（人提的需求） | `Task.prompt` |
| PR 的测试改动 | `Task.check_cmd` |
| Ticket 的 stage | 任务状态 |
| Executor 的 report | `Episode` 轨迹 |

这套映射已经落地成可运行代码。

## 五、代码

| 文件 | 作用 |
| --- | --- |
| `collect_real.py` | 从 GitHub 采集「Issue → PR → 测试」三元组 |
| `prepare_real.py` | 严格验证（三条校验），产出可用任务集 |
| `real_tasks.py` | 适配成 Task 接口（工作区构建 + 判定命令） |
| `run_real.py` | 用真实任务跑 agent 评测 |

产物：`results/real/`（`real_tasks.jsonl` 102 个候选、`verified_tasks.jsonl` 21 个可用）。

## 六、已知局限

1. **样本小**：只测了 2 个真实任务，因为每个 12–20 分钟。要做精确比例需要更多时间和配额。
2. **淘汰率高**：102 → 21（约 20%）。主因是只替换改动的源码文件不够，需要完整 PR diff 才能让真实修复跑通。
3. **环境依赖**：pip / attrs 的测试需要额外依赖（`installer`、`hypothesis`），当前镜像没装。
4. **未做 k 次采样**：真实任务上 pass^k 未测。

## 七、下一步（如需继续）

| 方向 | 做法 | 预期收益 |
| --- | --- | --- |
| 补全依赖 | 镜像里预装 `installer`、`hypothesis`、`pytest-xdist` | 可用任务从 21 增到 50+ |
| 应用完整 diff | 用 `git apply` 打 PR 的 patch 而非逐文件替换 | 减少「任务不可达」淘汰 |
| 跑满 21 个 | 每个 15 分钟，串行约 5 小时 | 得到精确通过率 |
| 训练价值验证 | 用真实任务的失败轨迹构造偏好对 | 有真实 gradient 的数据 |
