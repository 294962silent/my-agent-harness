# 稠密奖励评测：从 0/1 到逐步反馈

> 方向一（长程 Harness 工程 + 稠密奖励评测）的核心组件
> 531 条真实轨迹实测

## 一、为什么需要稠密奖励

现有的评测只有**终局判定**：

```python
reward = 1.0 if tests_all_passed else 0.0
```

问题在模型 100% 通过时完全暴露：

| 现象 | 后果 |
| --- | --- |
| 所有轨迹奖励都是 1.0 | 无法区分「一次做对」和「撞 10 次才做对」 |
| 没有中间信号 | 无法用于 GRPO（组内全同 → 优势为 0） |
| 无法定位退化 | 循环率 87.4% 这样的问题被掩盖 |

**稠密奖励把这些信息挖出来。**

## 二、四个可验证的奖励来源

全部基于代码事实，不引入 LLM 打分：

| 来源 | 规则 | 分值 |
| --- | --- | --- |
| **测试进展** | 每步跑测试，通过数从 a 涨到 b | +(b−a)/total |
| **回归惩罚** | 原本通过的测试变失败 | −0.3/个 |
| **目标文件命中** | 改的文件属于应改集合 | +0.2 |
| **无效动作** | 重复同一动作 / 连续跑测试不改码 | −0.02 ~ −0.03 |
| **终局奖励** | 全部通过 | +1.0 |

### 无测试快照时的动作分级

真实轨迹里没有记录每步的测试结果，因此按动作的信息价值给分：

| 动作 | 分值 | 理由 |
| --- | --- | --- |
| `edit` / `write` | **+0.4** | 产生实际改动，是真正的进展 |
| `bash` + pytest | **+0.1** | 验证行为，有价值但不可重复 |
| `read` / `ls` / `find` / `grep` | **+0.05** | 探索，信息价值低 |

## 三、实测结果

| 指标 | 值 |
| --- | --- |
| 轨迹数 | 531 |
| 成功率 | 1.000 |
| **平均稠密奖励** | **0.825** |
| **信号密度**（非零奖励步数占比） | **84.7%** |
| 平均非零步数 | 9.3 / 10.9 |
| 稠密/稀疏奖励比 | 0.82 |

### 与稀疏奖励的对比

| 奖励方式 | 非零信号数 | 可区分度 |
| --- | --- | --- |
| 稀疏（终局 0/1） | **1 个**（最后一步） | 全部为 1.0，无区分 |
| **稠密（本方案）** | **9.3 个** | 可区分撞运气 vs 一次做对 |

**信号密度 84.7% 意味着：一条 10.9 步的轨迹里有 9.3 步能获得反馈**，而稀疏奖励只有 1 步。

## 四、权重设计的过程（值得记录）

第一版权重得到 **−0.05** 的平均分（负数），检查后发现：

```
step 0 bash   gain=0     waste=0      total=0
step 1 bash   gain=0     waste=-0.05  total=-0.05
step 2 read   gain=0     waste=0      total=0
step 3 read   gain=0     waste=-0.05  total=-0.05
step 5 edit   gain=0.15  waste=0      total=0.15
```

问题：只有 `edit` 有正分（0.15），而重复动作一直扣分，**正负抵消**。

修正后：
- 按动作信息价值分级（edit 0.4 > bash+pytest 0.1 > 探索 0.05）
- 惩罚减弱（−0.05 → −0.02）

结果从 **−0.05 提升到 0.825**，信号密度 84.7%。

**这个调试过程本身说明**：稠密奖励不是「随便给点分」，权重要能反映真实的信息价值梯度。

## 五、与方向二（GRPO）的关系

GRPO 的核心是组内相对优势：

```
A_i = (r_i − mean(r_group)) / std(r_group)
```

如果所有轨迹的稀疏奖励都是 1.0，则 `std = 0`，**优势全为 0，无梯度**。

稠密奖励的价值：

| 场景 | 稀疏奖励 | 稠密奖励 |
| --- | --- | --- |
| 全部成功 | 全 1.0，无梯度 | 0.6–1.1 之间波动，**有梯度** |
| 全部失败 | 全 0.0，无梯度 | 过程分可区分「接近成功」和「完全没方向」 |

**这是让 GRPO 在饱和任务上也能训练的关键。**

## 七、局限与下一步

| 局限 | 说明 | 改进 |
| --- | --- | --- |
| 无真实测试快照 | 用了动作类型代理 | 在沙盒里每步跑一次测试（增加耗时约 2s/步） |
| 目标文件未用上 | 需要参考解法 | 从 PR diff 提取应改文件集合 |
| 未验证与成功率的正相关 | 任务全成功，无法测相关性 | 在失败样本上验证 |

**最重要的一条**：如果在**真实失败的轨迹**上验证「稠密分高的轨迹更可能成功」，才证明这个奖励设计是对的。当前任务集全成功，无法验证。
