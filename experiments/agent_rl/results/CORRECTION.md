# 修正：87.4% 的循环率是误报

> 这是一个自我纠错记录。原结论有误，特此更正。

## 一、原来的结论（错误）

`PROCESS_METRICS.md` 里报告：

| 指标 | 值 |
| --- | --- |
| 循环率（有 ≥3 次重复动作） | **87.4%** |
| 平均最长循环长度 | 4.03 |
| 时间视界 | 3.2 步 |

**典型样例**：`t4-011` 的 `bash` 连跑 11 次。

## 二、为什么错了

原来的 `detect_loop` **只看工具名**：

```python
tools = [c["tool"] for c in calls]   # 只有 "bash", "read", "ls"...
```

于是下面这个序列被判为「循环」：

```
bash(ls -la) → bash(find . -name "*.py") → bash(cat mod.py) → bash(pytest)
```

**但这是四次完全不同的动作**，是正常的探索：
- 第一次列目录
- 第二次找 Python 文件
- 第三次读文件内容
- 第四次跑测试

## 三、正确的判断标准

**「循环」应该定义为：同一工具 + 同一目标，重复执行而没有产生新信息。**

验证方式：用 `loop_breaker`（签名 = 工具名 + 关键参数 path/command/pattern）重新统计 531 条轨迹：

| 指标 | 只看工具名（错误） | **看工具+参数（正确）** |
| --- | --- | --- |
| 触发提示/换工具的轨迹 | 464（87.4%） | **5（0.9%）** |
| 被判定终止的轨迹 | — | **0（0.0%）** |

**从 87.4% 降到 0.9%。**

## 四、修正后的结论

### 1. 模型几乎不陷入真正的循环

531 条轨迹里只有 **5 条（0.9%）**出现了「同工具 + 同参数」的重复。

这说明模型在探索时**每次都会换参数**，不是机械重复。

### 2. 那 5 条是什么情况

| 特征 | 数据 |
| --- | --- |
| 都是成功轨迹 | 5/5 |
| 触发前都已经改过文件 | 5/5 |
| 平均触发位置 | 第 13.2 步 |

**解读**：这 5 条是「改完文件后反复跑同一个测试命令」，属于**验证型重复**，不是探索失败。而且它们最后都成功了。

### 3. 唯一真实的循环样例仍然存在

`t4-011` 的 `bash` 连跑 11 次——但检查命令内容后发现它也是**不同命令**（`ls`、`find`、`cat` 等），所以严格意义上也不算循环。

**原来的「典型样例」举证不成立。**

## 五、对方向一的影响

| 原计划 | 修正后 |
| --- | --- |
| 用循环打断器解决 87.4% 的循环问题 | ❌ **没有这个问题需要解决** |
| 时间视界 3.2 步说明长程能力差 | ⚠️ **需要重新计算**（原来基于错误的循环定义） |

### 时间视界需要重算

原定义：「连续无重复、无错误的最长步数」。这个定义本身可能是对的（衡量"连续推进"），但需要确认它不是在惩罚正常的工具切换。

## 六、保留的价值

虽然循环问题的结论错了，但**两个组件本身仍然有价值**：

1. **`loop_breaker.py`** —— 在**真正陷入循环**时（比如 SFT/GRPO 训练后模型退化），这是必要的护栏。离线验证显示它不会误伤正常探索（触发率 0.9%，且 5 条都是成功的验证型重复）。

2. **`dense_reward.py`** —— 稠密奖励与循环问题无关，仍然有效（信号密度 84.7%）。

## 七、教训

**指标定义错了，后面的所有分析都是错的。**

具体错在：
- 用「工具名」代替「动作语义」
- 没有先检查样例验证定义合理性
- 报告里写「典型样例」时没有真的去看命令内容

**修正做法**：任何指标，先在 5–10 条样例上人工验证，再跑全量。
