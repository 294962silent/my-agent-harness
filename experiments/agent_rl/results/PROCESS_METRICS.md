# 过程指标：长程行为的第一个实测基线

> 数据来源：531 条真实轨迹（`episodes_main_k5.jsonl` + `episodes_t7.jsonl`）
> 模型：DeepSeek V4.1 Flash · Docker 沙盒 · 纯代码判定

## 一、为什么需要过程指标

现有的 `pass^k / pass@k / gap` 只回答「**最终成没成**」：

| 指标 | 问题 |
| --- | --- |
| pass^k = 1.0 | 全对，看不出任何问题 |
| gap = 0 | 没有训练空间 |

**但「全对」不代表过程健康。** 长程 Harness 关心的是一路上有没有：

- 反复做同一件无用的事（循环）
- 卡住后能不能自救（恢复）
- 能连续保持有效行动多久（时间视界）

## 二、五个过程指标的定义

| 指标 | 定义 | 计算方式 |
| --- | --- | --- |
| **早停率** | 步数明显少于上限却没成功 | 失败且步数 < 50% 上限 |
| **循环次数** | 重复动作序列的最长长度 | 检测周期 1–6 的重复模式 |
| **恢复率** | 出错后 3 步内不再出错的占比 | 出错步的后 3 步是否正常 |
| **时间视界** | 连续无重复、无错误的最长步数 | 最长有效行动段 |
| **稠密奖励** | 每步的中间进度分 | 测试通过数增量 − 回归惩罚 |

## 三、实测结果

| 指标 | 值 |
| --- | --- |
| 轨迹数 | 531 |
| 成功率 | 1.000 |
| 平均步数 | 10.9 |
| 早停率 | 0.0 |
| **循环率**（有 ≥3 次重复动作） | **87.4%** |
| **平均最长循环长度** | **4.03** |
| 平均恢复率 | 1.0 |
| **平均时间视界** | **3.2** |
| 稠密/稀疏奖励比 | 1.1 |

## 四、结论

### 1. 「全对」掩盖了严重的循环行为

`pass^k = 1.0` 看起来完美，但**87.4% 的轨迹在过程中有 3 次以上的重复动作**。

**最典型的样例**（`t4-011`，循环长度 12）：

```
ls → find → read → read → read → bash → write → bash → bash
→ bash → bash → bash → bash → bash → bash → bash → bash → bash
```

`bash` 连跑 11 次——**反复执行同一条命令，不改代码**。它最终通过了，但过程是「撞运气」。

### 2. 任务越长，循环越严重

| 相关关系 | 数据 |
| --- | --- |
| 步数最多的 t3（16.0 步） | 循环率 96%、循环长度 5.36 |
| 步数最少的 t7（6.2 步） | 循环率 97%，但循环长度只有 2.97 |

**t3 的问题最严重**：平均 5.36 次连续重复，说明多文件重构时需要维持更长上下文，模型更容易失去方向。

### 3. 时间视界只有 3.2 步

即使任务平均 10.9 步，**连续不重复地有效行动只能维持 3.2 步**。

这与「长程 Harness」的目标直接冲突：**模型没有能力维持长程一致性**，靠的是一次次重新尝试。

### 4. 恢复率 1.0 是假象

因为绝大部分轨迹**最终都成功了**，所以「出错后 3 步内恢复」自然是 100%。
这个指标只在**有失败样本**时才有意义——合成任务全是成功，所以看不出区分度。

## 五、对目标的直接意义

对照「60% 方向一：长程 Harness 工程 + 稠密奖励评测」：

| 方向一要素 | 现状 |
| --- | --- |
| 过程指标 | ✅ 已实现五个指标并测出基线 |
| **早停率** | 0%，不是问题 |
| **循环** | ❌ **87.4% 有循环，是主要缺陷** |
| **时间视界** | ❌ **仅 3.2 步，是主要缺陷** |
| continue-until-timeout | ❌ 未实现，但**循环问题证明它必要** |
| 稠密过程奖励 | ⚠️ 已实现计算逻辑，但未接入训练 |

**改进方向已经明确**：

1. **循环检测与打断**——检测到重复动作时注入提示，强制改变策略
2. **时间视界延长**——通过稠密奖励引导模型保持有效行动，而不是撞运气
3. **稠密奖励接入 GRPO**——稀疏奖励在 100% 饱和时无梯度，稠密奖励能提供逐级信号
