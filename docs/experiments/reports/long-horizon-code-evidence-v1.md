# 长程代码 Harness 因果证据协议 v1

更新日期：2026-11-15。

## 结论先行

当前已有证据可以证明：

- My-Agent-Harness 在 Terminal-Bench 2.1 的 89 道代码与终端任务上完成过一次全量运行，通过 71/89；官方 Pi 为 72/89。
- 上下文产物开关做过 5 道 SWE-bench 小样本配对，开启组解决 2/5，关闭组解决 1/5；样本太小，不能据此宣称稳定收益。
- LongMemEval 96 题真实实验把查询时注入上下文从 105,316 tokens 降至 11,983 tokens，答案准确率从 71.9% 变为 69.8%。
- 受控策略探索完成 7/8 个 final 臂，但当前结果没有识别出训练策略收益。

当前证据不能证明：

- Terminal-Bench 的总体成绩由五层压缩、长期记忆、策略搜索或调度恢复中的某一个模块单独带来。
- 每个设计点都已经被真实长程代码实验证明有效。
- 本实现的代码通过率整体优于官方 Pi。

因此，面试回答必须区分“端到端能力”“机制正确性”“因果性能收益”三层，不能再用 Terminal-Bench 的单一总分证明每一个模块。

## 为什么 Terminal-Bench 2.1 只能回答一部分问题

Terminal-Bench 2.1 是 89 个相互隔离的多轮代码与终端任务，能够检验文件操作、命令执行、调试、测试和迭代修复。它的强项是覆盖面，不是单个任务的持续时长：全量套件总耗时约 22 小时，但这是 89 题累计值，平均约 15 分钟一题。

它无法单独验证：

- 同一仓库跨多个里程碑连续推进数小时。
- 进程终止后从 checkpoint 恢复并保持预算不重置。
- 新需求插入后是否仍遵守早先约束。
- 跨会话记忆是否正确处理过期事实和作用域。
- 策略学习能否在未见任务上复现。

因此，Terminal-Bench 用来回答“整个系统能否完成多种真实代码任务”；各设计点需要独立故障注入和 leave-one-out 消融来回答“这个机制具体修复了什么”。

## 基线定义

所有比较使用同一模型版本、同一任务快照、同一工具 schema、同一请求、Token、时间预算、同一评分器和同一系统提示核心。只允许目标机制不同。

### B0：最小 ReAct 基线

- 保留模型调用、文件读写、shell 和官方任务评分。
- 历史消息直接追加，不启用五层压缩和 artifact 外置。
- 不启用长期记忆。
- 不启用跨进程 checkpoint/resume。
- 不启用受控策略搜索。

### FULL：完整 Harness

在 B0 上启用当前产品的默认五层压缩、artifact 回读、版本化记忆、调度恢复与受控策略层。

### LOO-X：完整 Harness 去掉一个机制

每个机制单独进行 leave-one-out：

- LOO-CTX：关闭五层压缩和 artifact 投影。
- LOO-MEM：关闭长期记忆检索。
- LOO-REC：关闭 checkpoint/resume 与取消后的恢复。
- LOO-SEARCH：关闭受控策略搜索，固定为 reference policy。
- LOO-HOST-EVAL：允许候选程序自报分数，不进行宿主重算。

LOO 用于定位单个机制是否消除对应故障；B0 对 FULL 用于回答整体能力。不能只挑 FULL 成功而 Pi 失败的题来制造优势。

## 详细实验矩阵

| 技术点 | 预注册任务 | 故障触发 | 基线失败判据 | FULL/LOO 通过判据 | 主指标 |
|---|---|---|---|---|---|
| 五层压缩与 artifact 回读 | 多文件修改、长测试日志、跨 20+ 轮任务 | 早期证据被大输出挤出有效上下文；摘要遗漏具体错误行 | B0 或 LOO-CTX 无法提交正确修复，或请求超过固定 context budget | FULL 仍能在固定预算内检索、修改并通过最终测试 | 官方通过率、约束保持率、context token、artifact 回读成功率 |
| 调度、取消与文件锁 | 并行修改同一文件、取消后重跑、长任务中途插入 Steering | 两个写入竞争同一文件；取消留下僵尸进程或半完成写入 | B0 出现 lost update、残留进程、重复修改或无法继续 | FULL 串行化冲突写入、清理资源并从安全点继续 | 最终测试通过、冲突率、残留进程、重复请求数 |
| checkpoint/resume | 三阶段仓库任务，在第 1/2 阶段之间强制终止进程 | 新进程启动后内存状态消失 | B0 从头重跑、重置预算或无法恢复阶段状态 | FULL 从 journal/checkpoint 续跑，已完成请求不重放 | 恢复成功率、重复请求、重复评分、预算偏差 |
| 长期记忆 | 多会话仓库修改，含 API 契约、版本更新和冲突旧事实 | 早期约束被压缩；错误作用域或旧 revision 被召回 | B0 或 LOO-MEM 使用旧事实，最终测试失败 | FULL 校验 scope/identity/revision 后读取当前事实 | 最终测试通过率、约束遗忘率、stale-fact 使用率 |
| 受控策略搜索 | 留出的代码实验任务集，固定 train/holdout/final | 固定策略在 train 上偶发高分；候选预算与顺序影响结果 | reference/random 无法在 holdout 与 final 复现改善 | FULL 只在 holdout 严格改善时晋升，final 独立复现 | final 通过率、每成功任务成本、非法晋升数、回滚正确率 |
| 宿主评分与沙箱 | 候选程序伪造分数、写额外文件、访问网络或越界写 | 候选自报高分或篡改评测产物 | B0 信任自报分数或接受越界副作用 | FULL 拒绝交付并保持基线策略 | 攻击阻断率、错误晋升数、容器清理成功率 |

## 实验阶段

### Phase A：确定性故障注入

目的：证明机制本身确实修复了已知故障，而不依赖供应商随机性。

每个机制至少 20 次重复。使用真实生产组件、真实文件系统、真实 Docker 边界和脚本化模型动作；模型只负责触发预定义工具序列，便于隔离 Harness 行为。

报告字段：

- baseline 失败次数和错误类别。
- enhanced 通过次数。
- 最终代码测试结果。
- artifact 命中/回读次数。
- 重复请求、重复评分、残留进程和越界写入数量。
- 相同预算下 context token、总 token 和耗时。

Phase A 可以支持“机制能修复该故障”，不能支持“真实模型任务提升”。

### Phase B：公开代码任务配对

目的：检验修复是否在真实模型任务上转化为成功率和成本变化。

任务来源优先使用已冻结 revision 的 Terminal-Bench 2.1 CPU 任务和 SWE-EVO Dask 任务。正式扩样前先跑 6 个任务：

- 2 个长输出/上下文任务。
- 2 个多轮调试与版本控制任务。
- 2 个需要跨步骤约束保持的任务。

每个任务至少运行 B0、FULL，并针对目标机制运行一个 LOO 臂。先做单次配对检查 schema、环境与评分是否有效，再扩到至少 3 个独立 seed/repeat。没有完整终态或用量未知的 trial 不进入成功率分母，单独列为 infrastructure blocked。

成功标准：

- 官方评分通过。
- 同模型、同工具 schema、同预算。
- B0/FULL 任务身份一致。
- 无 unknown usage、重复评分或残留容器。
- 报告差值、配对 discordant cases、精确检验/置信区间和完整成本。

### Phase C：连续仓库长程任务

目的：回答 Terminal-Bench 无法覆盖的持续工程问题。

设计 3 组固定任务，每组包含 4 到 6 个里程碑：

- 第 1 组：持续新增兼容功能，旧 API 行为必须在最终阶段仍通过。
- 第 2 组：命令输出超过 context budget，必须依靠 artifact 证据定位问题。
- 第 3 组：第二阶段强制终止进程，第三阶段从 checkpoint 恢复并完成最终回归。

每个任务同时在会话开始时写入 3 到 5 个约束，其中至少一个在后续被更新。最终评分同时检查：

- 全部里程碑完成率。
- 最终回归测试。
- 过期约束误用率。
- 恢复后的工作损失和重复执行次数。
- 每成功任务总 token、费用和时间。

Phase C 才可以直接支撑“长程代码开发能力”。

## 当前可用的面试回答

“我没有把 Terminal-Bench 的 71/89 解释成四个模块分别带来的提升。它证明系统能完成多种真实代码与终端任务。单个机制我用故障注入和 leave-one-out 验证；其中 artifact 开关在 5 道 SWE 小样本上是 2/5 对 1/5，但不显著，策略探索也没有识别出学习收益。因此简历强调的是已经实现和验证的控制机制，不宣称每个模块都提高了 Terminal-Bench 通过率。”

这比把相关性说成因果更可信。对于尚未完成的实验，回答应明确标成待验证或负结果。

## 写入简历的门槛

只有满足以下条件，才能写成“某机制提升了长程代码任务”：

1. 机制特定故障在重复实验中被稳定消除。
2. 公开代码任务中至少完成预先冻结的配对样本。
3. 最终评分、用量和失败分类完整。
4. 差异经过配对统计，且排除同预算增加带来的解释。
5. 未出现 unknown usage、未解释的环境失败或事后换题。

未达到门槛时，统一写“实现了某机制，并通过故障注入或小样本 smoke 验证”，不写“显著提升成功率”。
