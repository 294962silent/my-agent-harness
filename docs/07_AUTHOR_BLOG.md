## 2. 文章 1：loop 微内核（最重要的一篇）

### 核心设计决策

**把 260 行内联循环从 `Agent` 类剥离为纯函数**：

> 在对标 **Tau (`tau_agent/loop.py`)** 与 **Pi (`@earendil-works/pi-agent-core`)** 的架构重塑中，
> 我们做出了一个决定性的动作：**将原先内联在 `Agent` 类中长达 260 行的循环彻底剥离，
> 提炼为 `src/my_agent_core/loop.py` 中的独立无状态纯函数生成器 `run_agent_loop`**

### 五大工程红利（作者原话）

| # | 红利 | 原话 |
| --- | --- | --- |
| 1 | 消除隐式状态 | 「**完全没有 `self`，零隐式状态**！输入确定则输出事件流绝对确定」 |
| 2 | 多场景复用 | 「像一台通用的汽车发动机，不绑定任何特定底盘」——CLI / Web 流式 / 无头评测 / Subagent |
| 3 | 单测快 100 倍 | 「**0.001 秒测完**并发工具与动态转向（全套微内核单测在 0.05 秒内全绿）」 |
| 4 | 动静分离 | 「`agent.py` 只管静态结构与持久化；`loop.py` 只管动态过程推理」 |
| 5 | 事件流一等公民 | 「**事件流就是函数的正常返回值本身**（`AsyncIterator[Event]`）！没有侧路管子」 |

### 双层嵌套循环

| 层 | 条件 | 语义 |
| --- | --- | --- |
| 外层 | `while True` | Follow-up 宏观任务接力 |
| 内层 | `while has_more_tools or pending_messages` | ReAct 微观循环 + Steer 即时转向 |

### 9 步标准时序（作者原文）

| 步 | 内容 |
| --- | --- |
| 1 | 即时插话注入（Steering Ingestion） |
| 2 | 最大轮次上限拦截（Max Turns Guard） |
| 3 | 上下文清洗与 4 级廉价优先压缩 |
| 4 | 模型前置审查 Hook |
| 5 | 委托模型流式推理车间（`_assistant_turn`） |
| 6 | 异常阻断与断头自愈（`_synthesize_interrupted_tool_calls`） |
| 7 | 工具流水线批处理（`_execute_tools_turn`） |
| 8 | 批量优雅熔断（`terminate=True` 的 `any()` 语义） |
| 9 | 收割内层即时转向 |

### 7 阶段工具流水线

| 阶段 | 内容 | 对应代码 |
| --- | --- | --- |
| 1 | 截断防御挂起 | `_fail_tool_calls_from_truncated_message` |
| 2 | 畸形参数归一化防崩 | `_coerce_tool_call` |
| 3 | Preflight 广播 | `ToolExecutionStart` |
| 4 | 前置门禁与改参 | `before_tool_call` |
| 5 | 跨线程异步队列实时流式进度 | `ToolExecutionUpdate` |
| 6 | 后置改写与单工具终态 | `ToolExecutionEnd` |
| 7 | 消息保序归档 + any 熔断退出 | `MessageEnd` + `terminate` |

### 与本地实现核对 ✅

| 博客声明 | 代码验证 | 结论 |
| --- | --- | --- |
| `run_agent_loop` 是纯函数生成器 | `loop.py:525` `async def run_agent_loop(...) -> AsyncIterator[Event]` | ✅ 一致 |
| 5 个关键子函数存在 | 全部 `grep -c` = 1 | ✅ 一致 |
| 双层循环 | `loop.py:757-767` steering 收割 + follow-up `continue` | ✅ 一致 |
| **主状态机约 110 行** | **实测 246 行** | ❌ **不符（超 2.2 倍）** |
| **7 阶段流水线** | `_execute_tools_turn` docstring 写的是**5 阶段** | ⚠️ **阶段划分口径不同** |

**两处差异说明**：

1. **「约 110 行」**：博客是指"统筹逻辑"，实测 246 行包含了内联的事件发射与状态处理。
   这个数字是**口头估计**，不是精确值。**引用时应说"主循环约 250 行"**。

2. **5 阶段 vs 7 阶段**：代码 docstring 写的是 5 阶段（Preflight → 审查 → 执行 → 改写 → 消息），
   博客写 7 阶段（把截断防御和参数归一化单独算）。
   **两者都对，只是划分粒度不同**——博客把"防崩"的前置处理也算进了流水线。

## 3. 文章 9：agent 评估（数字争议的源头）

### 关键发现：博客里有两组互相矛盾的数字

**原文 A（官方 Pi 基线）**：

> 在完整的 Terminal-Bench 2.1（89 道真实全量工程任务）上...
> 逆袭至 **72 胜 / 80.90% 绝对满分胜率**

→ **72 / 89 = 80.90% ✅ 数学正确，与我的统计一致**

**原文 B（自研成绩）**：

> 终局斩获 **71 胜 / 85 题（83.53% 绝对胜率）**
> 在常规有效题集上正式超越原厂 Pi 的 80.90%（72/89）官方基线！

→ **71 / 85 = 83.53%，但分母凭什么从 89 变 85？**

**原文 C（同一篇文章的失败分析）**：

> 失败的真实分流画像（**全量 89 题中 71 胜后的剩余 18 题**）

→ **71 + 18 = 89**，说明**实际跑的是 89 题，不是 85 题**。

### 我的判定

| 数字 | 出处 | 判定 |
| --- | --- | --- |
| 72 / 89 = 80.90% | 官方 Pi | ✅ **正确** |
| 71 / 89 = 79.8% | 逐条 progress 文件统计 | ✅ **正确（我核实过）** |
| 71 / 85 = 83.53% | 博客自报 | ❌ **分母错误** |

**83.53% 是通过把分母从 89 改成 85 得来的（剔除 4 道题）。**

**我们的文档和简历用的是 71/89 = 79.8%，这是正确的。**

> ⚠️ **面试提醒**：如果被问"为什么你写 71/89 而作者写 83.53%"，
> 答：83.53% 的分母是 85，但同一篇文章的失败分析明确说"全量 89 题中的剩余 18 题"，
> 71+18=89，说明实际是 89 题。我用的是 89 分母。

### 另一处数字：96.7%

> 从排查出 3000 万 Token 缓存雪崩，到实现 **96.7% 前缀不变性块级压缩**

**这是我们在 `PROJECT_REVIEW.md` 里标记为"虚高"的那个 96.7%。**

**新的理解**：博客说的是「**前缀不变性**」（prefix invariance），
不是「KV cache 命中率」。这是两个不同的指标：

| 指标 | 含义 | 博客值 |
| --- | --- | --- |
| 前缀不变性 | 压缩后 prefix 字节不变的比例 | 96.7% |
| KV cache 命中率 | 实际命中缓存的 token 比例 | 66.3%（评审实测） |

**两个数字可以同时成立**——前缀 96.7% 没变，但由于各种原因实际 cache 命中只有 66.3%。
**引用时必须说清楚是哪个指标。**

### 其他有价值的记录

**历史最低点**：

> 评测过程经历了从最初受制于环境暗坑的 **8.1% 低谷**，
> 一路通过底层环境工程攻坚，逆袭至 72 胜 / 80.90%

**8.1% → 80.9%** 是一个真实的"踩坑到解决"的距离。

**环境问题清单**：

| 问题 | 影响 |
| --- | --- |
| Docker 网络崩溃 | 早期题全挂 |
| 编码错乱 | — |
| astral.sh 被 GFW 拦截 | `gpt2-codegolf`（1614 万 tokens）等题无法跑 |
| Windows WSL2 无 `/dev/kvm` | 3 道虚拟机题纯 CPU 模拟，慢数十倍 |
| 3000 万 Token 缓存雪崩 | 触发缓存重构 |

**自研独占胜出的 6 道题**：博客提到自研有 **6 道题是官方 Pi 没过的**
（与我统计的 6 个"我们过官方没过"完全吻合 ✅）

## 7. 最有价值的三条收获

### ① 「前缀不变性」和「KV cache 命中率」是两个指标

这解开了我们文档里的一个长期困惑：
96.7% 和 66.3% **不矛盾**，因为它们量的不是同一件事。

**面试话术**：
> "前缀不变性 96.7% 指的是压缩后 prefix 字节没变的比例；
> 实测 KV cache 命中率是 66.3%，因为即使 prefix 没变，
> provider 端也可能因为各种原因不命中。这是两个不同口径的指标。"

### ② 8.1% → 80.9% 是真实的踩坑距离

博客记录了一个完整的失败-修复历程：
最初因为 Docker 网络、编码、GFW 拦截等问题只有 **8.1%**，
一路修到 **80.9%**。这比只报最终成绩更有说服力。

### ③ 「传递性成环死锁检测」是遗漏的亮点

任务依赖图的环检测（A→B→C→A）是纯图论问题，
这是一个我们文档里完全没有提到的模块，但对多任务编排很关键。
