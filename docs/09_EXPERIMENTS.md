# 模块 1：ReAct 微内核

## 实验 1-A：纯函数 vs 类封装

**假设**：纯函数生成器无需装配整个 Agent，单测更快、内存更省。

**方法**：纯 `run_agent_loop(InstantLLM, [])` × 20 次 vs 完整 `Agent(...)` 构造 × 10 次。

| 组 | 耗时 | 峰值内存 |
| --- | --- | --- |
| **纯函数** | **0.366 ms** | **6.6 KB** |
| 类封装（完整 Agent） | 3.859 ms | 43.0 KB |
| **差异** | **快 10.5×** | **省 85%** |

**结论**：✅ 假设成立。纯函数写法在单测场景下快一个数量级、内存省 85%。

**注**：作者博客称「单测快 100 倍」，实测是 **10.5×**。
100× 可能是指「整套微内核单测 0.05 秒 vs 之前需装配」，口径不同。

**复现**：`uv run python -m experiments.per_module.exp_module1_loop`

## 实验 1-B：自动续写（截断自愈）

**假设**：模型输出被 `max_tokens` 截断时，自动续写能挽回一次完整工具调用。

**方法**：
- 场景 A（无截断）：第 1 次直接返回 `tool_calls`
- 场景 B（先截断）：第 1 次 `stop_reason=length` 无工具，第 2 次给 `tool_calls`

| 场景 | 工具执行 | 模型调用次数 |
| --- | --- | --- |
| A 无截断 | ✅ 是 | 23 |
| **B 先截断** | ✅ **是** | **25** |

**结论**：✅ **截断场景仍拿到了工具**（额外 2 次模型调用）。
如果没有续写机制，场景 B 会直接结束、0 个工具执行。

**复现**：同 1-A

## 实验 1-C：Steering / Follow-up 两级干预

**假设**：两级干预都能延长会话，但收割时机不同。

**方法**：4 种注入组合，比较模型调用次数。

| 场景 | 模型调用 | 相对基线 |
| --- | --- | --- |
| 基线（无干预） | 1 | — |
| 仅 steering（3 次） | 3 | **+2** |
| 仅 follow-up（1 次） | 2 | **+1** |
| 两者都有 | 4 | **+3** |

**结论**：✅ 两种干预独立生效且可叠加（+2 +1 = +3）。

**重要发现（实验设计修正）**：
steering 只在**内层循环内**收割。如果模型第一轮就 `end_turn` 且无工具调用，
内层已退出，steering 不会被处理。这是设计如此（不是 bug）——
steering 的语义是「打断正在进行的多步执行」。

**复现**：同 1-A

# 模块 2：工具执行与并发

## 实验 2-A：批级门控 vs 全并发

**假设**：批级门控在保证正确性的同时，只读批次能获得并发收益。

**方法**：三种批次组成，用「写后读版本号」检测竞态（写先 sleep 再递增，读立即读）。

| 批次 | 耗时 | 读到的版本 | 正确性 |
| --- | --- | --- | --- |
| 5 个只读 | **12.1 ms** | v0 | — |
| **批级门控**（1写+4读） | 91.9 ms | **v1,v1,v1,v1** | ✅ **正确** |
| **强制全并发** | **29.6 ms** | **v0,v0,v0,v0** | ❌ **读到旧值** |

**结论**：✅ **这是本组最有说服力的实验**。

- 批级门控多花 **62 ms**（3.1×），换来 **100% 正确性**
- 强制全并发快 3.1×，但 **4 个读全部读到写入前的旧值**（竞态）

**面试话术**：
> "我用 62 毫秒的延迟换 100% 的正确性。全并发快 3 倍，但 4 个读工具全部读到旧值。"

**复现**：`uv run python -m experiments.per_module.exp_module2_registry`

# 模块 4：会话树

## 实验 4-A：Fork 成本 ⚠️ **发现真实缺陷**

**假设（原始）**：树状 fork 是 O(1)，线性结构是 O(n)。

**实测结果与假设相反**：

| 消息数 | 树状 fork | 线性拷贝 | 树状新增字节 | 线性新增字节 |
| --- | --- | --- | --- | --- |
| 100 | **322 ms** | 0.93 ms | 13.6 KB | 3.9 KB |
| 1000 | **3,239 ms** | 1.02 ms | 134.9 KB | 39.9 KB |
| 5000 | **16,754 ms** | 2.01 ms | 677.9 KB | 203.9 KB |

**增长**：100 → 5000 条，树状 fork 慢 **52×**（线性增长）；线性拷贝几乎不变。

**根因定位**（`session.py:553`）：

```python
def fork(self, entry_id: str, new_path: Path | None = None) -> Session:
    new_session = Session(path=new_path, ...)
    for entry in self.tree.get_path_to_entry(entry_id):
        if isinstance(entry, MessageEntry):
            new_session.add_message(entry.role, entry.content, **entry.metadata)
            # ↑ add_message 内部调用 self.save() → 全量重写文件
```

**`fork()` 逐条 `add_message`，每条都触发 `save()` 全量重写** → O(n²) 次磁盘写入。

**这说明什么**：

| 层 | 是否 O(1) |
| --- | --- |
| **数据结构**（Entry 树 + parentId） | ✅ 是，天然 O(1) |
| **落盘实现**（fork 遍历 + 逐条 save） | ❌ 否，O(n²) |

**这是一个真实的性能缺陷**：树结构的优势被落盘实现拖累了。

**修复方向**（未实施）：
1. fork 时批量写一次，而非逐条 save
2. 或者用硬链接/写指针记录，真正 O(1)

**诚实标注**：这个实验**证伪了原始假设**，但暴露了真实问题，比"验证成功"更有价值。

**复现**：`uv run python -m experiments.per_module.exp_m4_session`

## 实验 4-B：增量追加 vs 全量重写（P1-2 缺陷量化）

**假设**：增量追加写入量 O(n)，全量重写 O(n²)。

**方法**：200 条消息，每条 200 字符。

| 组 | 总写入字节 | 耗时 |
| --- | --- | --- |
| 全量重写 | **5,007,995** | 126.2 ms |
| **增量追加** | **49,890** | **1.4 ms** |
| **差异** | **100.4×** | **87.3×** |

**结论**：✅ 全量重写写入量是追加的 **100 倍**，耗时 87 倍。
这量化了 `PROJECT_REVIEW.md` 里 P1-2 缺陷的严重性。

**理论验证**：n=200 时，O(n²)/O(n) = n/2 = 100。**与实测 100.4 完全吻合**。

**复现**：同上

## 实验 7-C：组合风险漏检 ⚠️ **主动证伪**

**背景**：SCR-Bench（2026-06）论文指出「孤立良性、组合有害」。

**方法**：分别评估两个操作的风险等级。

| 操作 | 独立风险等级 |
| --- | --- |
| `read(".env")` | **低（l）** |
| `write("public/x.txt")` | **中（m）** |
| **组合（密钥泄漏）** | ❌ **无任何一级能识别** |

**结论**：⚠️ **确认缺陷存在**。

两个操作各自合法、均未达阻断阈值；但 `read(.env)` → `write(public/)` 构成密钥泄漏。
**当前的工具级门禁无跨调用状态，无法表达组合风险。**

**这是本组唯一一个"验证失败"的实验**，但它**证明了学术论文的批评成立**，
对文档价值大于一个"通过"的实验。

**面试话术**：
> "我自己做了个实验证明这个设计有漏洞：`read(.env)` 是低风险、
> `write(public/)` 是中风险，单独看都合法。但组合起来就是密钥泄漏，
> 而我的工具级门禁完全看不到。SCR-Bench 那篇论文说的就是这个。"
