## 0. 一个重要的元发现：Harness 本身已成为研究对象

2026 年出现了三篇直接研究 **agent harness 架构**的论文，这让我们这个项目的定位发生了变化——
它不再是"又一个 agent 框架"，而是**有明确学术坐标系的一个实例**。

| 论文 | 时间 | 核心贡献 | 与本项目的关系 |
| --- | --- | --- | --- |
| **From Question Answering to Task Completion: A Survey on Agent System and Harness Design** (arXiv 2606.20683) | 2026-06 预印本 | 把 agent 拆成「模型 + harness」，harness 有 6 项运行时职责：observation / context / control / action / state / **verification** | **本项目的 5 个模块几乎逐一对应**，但 verification 未被我们提为一等公民 |
| **Architectural Design Decisions in AI Agent Harnesses** (arXiv 2604.18071) | 2026-04 预印本 | 70 个公开 agent 项目的**源码级实证**：主流是文件持久化/混合/分层上下文策略；「中间层隔离普遍、**高保证审计罕见**」 | **直接实证了我们「落盘 + 摘要 + 子代理隔离」的设计选择** |
| **Scaling Laws for Agent Harnesses via Effective Feedback Compute (EFC)** (arXiv 2605.29682) | 2026-05 预印本 | 用「有信息量、非冗余、被保留的反馈」作为 scaling 坐标，R²=0.93（原始 compute 近乎零拟合） | 提供了 harness 级别的量化框架；我们的实验未做此类建模 |

**这张表的价值**：面试时可以这样讲——
> "我的设计选择不是拍脑袋。2026 年有篇 70 个 agent 项目的源码级实证论文
> (arXiv 2604.18071)，结论是主流做法就是文件持久化 + 分层压缩，
> 而且『高保证审计』普遍缺失。我的实现属于主流路线，
> 审计链是我已知的缺口。"

## 1. 上下文压缩：我们缺「该不该压」的门控

### 对标论文

| 论文 | 会议/时间 | 核心方法 | 与本项目的异同 |
| --- | --- | --- | --- |
| **ACON: Optimizing Context Compression for Long-horizon LLM Agents** (2510.00615) | **ICML 2026** | 在自然语言空间用**失败分析**迭代精炼压缩准则，无需微调 | 我们的摘要准则是**静态的**（一次性写死），ACON 是**从失败中演进**的 |
| **Don't Break the Cache: Prompt Caching for Long-Horizon Agentic Tasks** (2601.06007) | 2026-01 | 跨三家 provider、500+ session：成本降 41-80%、TTFT 改善 13-31%；**朴素全量缓存反而拉高延迟** | **直接量化依据**了我们的 prefix cache 保护；也警告了「在历史中段插入摘要会打断 cache 前缀」 |
| **KVFlow: Efficient Prefix Caching for Multi-Agent Workflows** (2507.07400) | **NeurIPS 2025** | Agent Step Graph + steps-to-execution 值指导 KV node 级驱逐，相对 SGLang 1.83×/2.19× | **暴露我们未考虑的点**：多子代理并发时，服务端会把子代理 KV 当低优先级驱逐 |

### 我们的设计 vs 学术

| 维度 | 本项目 | ACON | Don't Break the Cache | KVFlow |
| --- | --- | --- | --- | --- |
| 压缩触发 | 80% 阈值 | 失败驱动 | 块级控制 | 图驱动 |
| 准则演进 | ❌ 静态 | ✅ 迭代精炼 | — | — |
| Cache 保护 | ✅ Append-Only + 落盘 | — | ✅ 量化验证 | ✅ KV 级 |
| 多子代理 | ❌ 未考虑 | — | — | ✅ |

### 诚实的差距

1. **我们缺「该不该压」的门控**。ACON 用失败分析决定压缩准则；
   我们是"到 80% 就压"，不判断这次压缩会不会丢关键信息。
   （另有一篇 GRU-Mem 报告门控带来 400% 加速，我们未做此优化）
2. **我们无多子代理场景的 cache 分析**。KVFlow 证明子代理并发会相互驱逐 KV。
   我们的子代理实现没有考虑这点。

### 我们的优势（相对学术）

**「免费层」的工程价值**：ACON 等论文的压缩都要过模型（贵）；
我们的第 1 层是**纯本地操作**（工具输出落盘），零 LLM 调用。
这在工程上是很实际的设计，学术论文往往不强调。

## 2. 记忆系统：我们的三层和 Mem0 同名，但缺冲突消解

### 对标论文

| 论文 | 时间 | 核心方法 | 与本项目的关系 |
| --- | --- | --- | --- |
| **Mem0** (2504.19413) | 2025-04 | 抽取→巩固→检索三阶段（**与本项目命名完全一致**），LOCOMO 上 p95 延迟 -91%、token -90%+ | 巩固是**冲突消解式更新**；我们若只做摘要不做消解，会产生陈旧事实并存 |
| **A-MEM: Agentic Memory** (2502.12110) | **NeurIPS 2025** | Zettelkasten 卡片盒：结构化 note + 自动建链 + **memory evolution**（新记忆回写更新旧记忆） | **Markdown + frontmatter + 双链即可复现其核心机制**——这是"Markdown 不是学术落后"的最佳论证 |
| **LongMemEval** (2410.10813) | **ICLR 2025** | 五能力评测，含 **abstention（拒答）**；商业助手跨 session 掉 30% | 我们的评测基准 |

### 我们的实现（`memory_index.py`）与 A-MEM 的对比

| 机制 | 本项目 | A-MEM |
| --- | --- | --- |
| 存储 | Markdown | Markdown + frontmatter |
| 结构化 | `Fact(subject, key, value)` | note（上下文描述 / 关键词 / 标签） |
| 冲突处理 | ✅ **双层时间**（`valid_from`/`valid_to` + history 链） | ✅ memory evolution（回写更新） |
| 自动建链 | ❌ | ✅ 自动链接相关 note |
| 检索 | BM25 / FTS5 | 嵌入 + 链接遍历 |

**一个值得说的点**：我们的**双层时间建模**在学术上是有对应物的
（bi-temporal modeling），而且比 Mem0 的"更新"更保守——我们保留完整历史。
这在"用户偏好随时间变化"的场景下更严谨。

### 诚实的差距

| 缺失 | 影响 | 对应论文 |
| --- | --- | --- |
| 自动建链 | 无法发现"Python 版本"和"测试框架"的关联 | A-MEM |
| 程序性记忆 | 只记事实，不记"怎么做" | AWM (Agent Workflow Memory) |
| **abstention 能力** | 记忆里没有时，不会说"我不知道"，而会瞎猜 | LongMemEval 五能力之一 |
| 指针式层间路由 | 所有记忆平铺，无分层 | H-MEM |

## 3. 长程任务：我们的两层 Loop 是"部分解药"

### 对标论文

| 论文 | 时间 | 核心洞察 | 与本项目的关系 |
| --- | --- | --- | --- |
| **Why Reasoning Fails to Plan (FLARE)** (2601.22311) | 2026-01 | step-wise reasoning 诱导逐步贪心，**早期短视承诺被系统放大**；用 lookahead + 价值传播 + **有限承诺**解决；LLaMA-8B+FLARE 常超 GPT-4o | **项目的两层 Loop 的理论诊断**：内层 ReAct = 贪心（已知缺陷），外层 Task 队列 = 部分解药，**缺「有限承诺」** |
| **Demystifying RL for Long-Horizon Tool-Using Agents** (2603.21972) | 2026-03 | 5 轴分解 7 条结论；关键：**环境稳定性对防止策略退化至关重要** | 直接映射本项目「非安全工具串行 + 单文件排队锁」是**正确性前提**而非纯性能设计 |
| **CodePlan** (FSE 2024) | 2024 | 仓库级编码 = 规划问题：增量依赖分析 + change may-impact + 自适应规划 | 我们的 Task 队列应由此驱动排序 |

### FLARE 对本项目的诊断（这是最有价值的一条）

**FLARE 说的「逐步贪心」正是我们内层 ReAct 的本质**：

```
内层 ReAct：每步只问"下一步做什么最好"
     ↓
    一旦早期选错方向（比如先改错了文件），
    后续所有步骤都在错误基础上"局部最优"
```

**我们的两层 Loop 是部分解药**：

| 层 | 对治什么 | 缺什么 |
| --- | --- | --- |
| 内层 ReAct | 单步执行 | ❌ 天然贪心 |
| 外层 Task 队列 | 多任务间切换 | ❌ 无 lookahead 估值 |
| steering | 用户可纠正 | ⚠️ 依赖人 |

**缺的是「有限承诺」**：FLARE 的做法是让模型在早期决策上保留可回退性。
我们的树状会话**有这个基础设施**（`rewind` / `fork`），但**没有主动使用**——
即：不会"先试探性走两步，发现不对就回退"，只是被动等用户命令。

**这是一个真正值得写进文档的洞察**：
我们有回退的**能力**（树状存储），但没有回退的**策略**。

### 另一条直接支持

**Demystifying RL (2603.21972) 说「环境稳定性对防止策略退化至关重要」**——
这直接支持我们「非安全工具串行 + 单文件排队锁」的设计：

> 我们不是为了"性能"才做串行，是为了**保证环境稳定**。
> 如果工具并发导致文件读写竞争，模型看到的反馈是不确定的，
> 学习信号就会被污染。

这个论证让"批级串行"从一个保守选择，变成了**有理论依据的正确选择**。

## 4. 子代理：学术证明"增益往往很小"

### 对标论文

| 论文 | 时间 | 核心贡献 | 与本项目的关系 |
| --- | --- | --- | --- |
| **Why Do Multi-Agent LLM Systems Fail? (MAST)** (2503.13657) | 2025-03（Berkeley） | 7 框架 1600+ trace，**14 种失败模式 3 大类**（系统设计 / agent 间失配 / 任务验证）；核心结论：**MAS 增益往往很小** | 可直接当子代理验收 checklist |
| **Multi-Agent Collaboration via Evolving Orchestration** (2505.19591) | **NeurIPS 2025** | puppeteer 范式，orchestrator 用 RL 学调度；提升来自涌现的"更紧凑循环推理结构" | 支持本项目**中心化调度**而非对等协作 |

### MAST 的 14 种失败模式 → 我们的验收清单

MAST 把多智能体失败分成 3 大类，每类都可对应到我们的实现：

| MAST 类别 | 具体失败 | 本项目的风险点 | 我们的应对 |
| --- | --- | --- | --- |
| **系统设计** | 违反任务规范、步骤重复 | 子代理重复父代理已做的工作 | ⚠️ 无机制阻止 |
| **agent 间失配** | 信息丢失、上下文不一致 | 子代理只看得到父给的 prompt，看不到完整历史 | ✅ 上下文隔离是设计目标，但**信息丢失也是风险** |
| **任务验证** | 未验证就返回、验证不全 | 子代理说"完成了"但没跑测试 | ⚠️ 依赖父代理复核 |

### 关键结论：子代理不是免费午餐

**MAST 的核心结论「MAS 增益往往很小」** 对我们的启示：

我们实现了子代理机制，但**没有做过「子代理 vs 单 agent」的受控实验**。
学术调研显示：**这个实验至今没人做过**（见下方稀缺性判断）。

**这既是我们文档的缺口，也是一个差异化机会。**

## 5. 工具并发：这是我们可以"自居前沿"的地方

### 对标论文

| 论文 | 会议 | 核心方法 | 与本项目的关系 |
| --- | --- | --- | --- |
| **LLMCompiler** (2312.04511) | **ICML 2024** | Planner / Task Fetching Unit / Executor 三段，DAG 化并行函数调用；3.7× 延迟、6.7× 成本、+9% 准确率 | 本项目并发控制的**形式化语言基座** |
| **PASTE: Parallelizing Tool Execution and LLM Generation** (2603.18897) | 2026-03 | **隔离推测结果直到 LLM 确认**，任务完成时间 -43.5% | 我们的"只读并发"可升级为"只读推测预执行" |
| **Speculative Actions** (2510.04371) | 2025-10 | 快模型预测未来动作并行执行，命中才提交（lossless），延迟 -20% | 同上 |

### 我们的设计 vs LLMCompiler

| 维度 | 本项目（批级门控） | LLMCompiler（DAG） |
| --- | --- | --- |
| 粒度 | 批 | 调用级 |
| 依赖推导 | **不需要**（有写就全串行） | 需要（建 DAG） |
| 正确性 | **可证明**（无并发写） | 依赖图正确性 |
| 并行度 | 只读批次 | 更高 |

**为什么我们选保守方案**（第 04 文档已论证）：DAG 需要静态分析工具的读写集，
但 `bash` 无法静态分析，`edit` 的写入位置依赖文件内容。

### ⭐ 一个真正的前沿空白

学术调研的结论：

> **「工具并发控制的副作用语义理论」**：LLMCompiler（2024）之后**无直接继任者**；
> SCR-Bench 只做了安全侧的路径分析，**没有做调度侧的并发正确性分析**。

**这意味着**：
- 我们遇到的「批级 vs 工具级」权衡，**学术上没有标准答案**
- 我们的选择（批级、fail-safe 默认）是有工程依据的，但**缺乏理论刻画**
- **这是一篇论文的机会**：给"工具调度的副作用语义"建模

## 6. 评测：pass^k 比 pass@k 更适合 harness

### 对标论文

| 论文 | 时间 | 核心贡献 |
| --- | --- | --- |
| **τ-bench** (2406.12045) | 2024-06 | **pass^k**（k 次全过的概率）优于 pass@k；GPT-4o pass^8 < 25% |
| **Terminal-Bench 2.0** (2601.11868) | 2026-01 | 89 个 CLI 任务、前沿模型 <65%、附错误分析 |
| **TRACE: Benchmarking Reward Hack Detection** (2601.20103) | 2026-01 | **54 类 reward exploit**；对比式异常检测下识别率 45%→63% |

### 我们的评测 vs 学术标准

| 维度 | 本项目 | 学术建议 |
| --- | --- | --- |
| 基准 | Terminal-Bench 2.1（89 题） | ✅ **形态最匹配**（CLI + 工具 + 文件系统） |
| 主指标 | 通过率（71/89） | ⚠️ 应用 **pass^k** 而非 pass@k |
| 多次运行 | ❌ 单次 | ⚠️ τ-bench 建议 k≥8 |
| reward hack 检测 | ❌ 无 | ⚠️ TRACE 有 54 类 |

**诚实的差距**：
我们的 71/89 是**单次运行**结果。如果按 pass^3 标准（3 次全过），数字会显著下降。
**这是面试时可能被问到的点**——"你跑了几次？"

### 与 Direction 1 的呼应

我们在 Agent RL 方向做过的 **`pass^k = E[∏1(success_i)]`** 与 `gap = pass@k - pass^k`
的分析，**恰好与 τ-bench 的结论一致**。这说明两个方向在评测方法论上是打通的。

## 8. 安全与权限：2025-2026 最活跃的方向

### 对标论文

| 论文 | 会议/时间 | 核心方法 | 与本项目的关系 |
| --- | --- | --- | --- |
| **AgentBound** (2510.21236) | **FSE 2026** | Android 权限模型式**声明式策略** + 独立执行引擎；从源码自动生成策略准确率 80.9% | 我们的声明式策略可对标 |
| **AEGIS** (2603.12621) | 2026-03 | **执行前防火墙** + Ed25519/SHA-256 **哈希链防篡改审计**；48 攻击全阻断、误报 1.2%、延迟 +8.3ms | **我们缺审计链** |
| **OpenClaw PRISM** (2603.11853) | 2026-03 | **把强制执行分散到 10 个生命周期钩子**，含**子代理派生**；会话级风险累积 + TTL 衰减 | **与本项目「14 事件 / 5 钩子」结构最对应** |
| **CaMeL** (2503.18813) | 2025-03 | 控制流/数据流显式提取 + capability，不可信数据永不影影响程序流；AgentDojo 77% 可证明安全 | 我们无数据流分析 |
| **SCR-Bench** (2606.15242) | 2026-06 | **孤立良性、组合有害**：组合下攻击成功率 33.6% vs 孤立近 0 | **证明「只读/非安全」二分无法表达路径级风险** |

### SCR-Bench 对我们的直接批评

**这是对我们「只读/非安全」二分模型的正面挑战**：

> 单个工具是良性的，**组合起来有害**。
> 例子：`read("/etc/passwd")` 是只读的（良性），`write("x.txt", 内容)` 是写（会串行），
> 但 `read(.env)` → `write` 到公开目录 = 密钥泄漏。

**我们的批级门控只判断"有没有写"**，不判断"这个读的会不会泄漏到那个写"。

**这是一个真实的、学术已确认的漏洞类别**。

### 我们的钩子 vs PRISM 的十钩子

| 维度 | 本项目 | PRISM |
| --- | --- | --- |
| 钩子数 | 5 个 | 10 个 |
| **可阻断** | ✅ `HookResult.block` | ✅ |
| **子代理派生钩子** | ❌ **缺** | ✅ |
| 会话级风险累积 | ❌ | ✅ |
| TTL 衰减 | ❌ | ✅ |
| 审计链 | ❌ | ✅ (AEGIS) |

**「子代理派生」这个钩子点我们缺**：子代理继承父代理的权限，
但**子代理可能被 prompt injection 诱导**去做父代理不会做的事。
PRISM 把"派生子代理"作为一个必须设防的钩子点。

## 9. 稀缺性判断：哪些是我们能做原创的地方

> 基于 52 条引用的调研结论。

| 主题 | 学术供给 | 我们能否做原创 |
| --- | --- | --- |
| 0. Harness 元层 | 中等（2026 集中出现，均预印本） | ⚠️ 可对标但难超越 |
| 1. 上下文压缩 | **丰富** | ❌ 难 |
| 2. Agent 记忆 | **丰富** | ❌ 难 |
| 3. 长程任务规划 | 稀缺（新算法层） | ⚠️ 需理论功底 |
| 4. 多智能体 | 中等 | ⚠️ |
| 5. **工具并发控制** | **稀缺**（LLMCompiler 后无继任者） | ✅ **可自居前沿** |
| 6. Agent 评测 | 中等（harness 级归因稀缺） | ✅ 有机会 |
| 7. 代码 Agent | 评测饱和 / 架构稀缺 | ⚠️ |
| 8. 安全与权限 | **丰富且最新** | ❌ 难 |

### 四个明确的空白（可作差异化）

1. **工具并发控制的副作用语义理论**
   LLMCompiler（2024）之后无直接继任者；SCR-Bench 只做安全侧路径分析，
   没有做调度侧的并发正确性分析。
   → **我们的「批级 vs 工具级」权衡，学术上没有标准答案。**

2. **子代理委派的定量收益归因**
   只有失败分析（MAST）与架构实证（2604.18071），
   **没有「同等 token 预算下子代理 vs 单 agent 的收益曲线」的受控实验**。
   → 这是我们能做的实验。

3. **Harness 级 scaling law / 消融方法论**
   EFC（2605.29682）是孤例，尚无复现范式。

4. **树状会话结构作为规划原语**
   LATS 用树做搜索但不管会话持久化；harness 侧的树存储未与搜索理论打通。
   → **我们的 `fork`/`rewind` 基础设施正好是缺的那一半。**

## 11. 面试可以直接用的话术

### 为什么选这个架构

> "我做架构选择时参照了 2026 年一篇 70 个 agent 项目的源码级实证
> (arXiv 2604.18071)——主流就是文件持久化 + 分层压缩，而且『高保证审计』普遍缺失。
> 我的实现走的是主流路线，审计链是我清楚的缺口。"

### 关于工具并发

> "工具并发这块，学术上 LLMCompiler（ICML'24）之后基本没有继任者。
> 我用的是批级门控——只要有写操作整批串行。
> 这比 DAG 调度保守，但换来『永远不需要静态分析工具读写集』这个强保证，
> 因为 bash 工具的副作用无法静态分析。
> 这个权衡学术上没有标准答案，是我自己论证的。"

### 关于子代理

> "MAST（Berkeley，1600+ trace）的结论是多智能体增益往往很小，
> 列出 14 种失败模式。我实现了子代理机制，但老实说没做过
> 『同等 token 预算下子代理 vs 单 agent』的受控实验——
> 学术调研显示这个实验至今没人做过。"

### 关于评测

> "Terminal-Bench 2.1 上我 71/89，官方 Pi 72/89，
> 但 token 省 66%、费用省 75%。逐任务看是 6 胜 7 负的交叉分布，
> 说明不是复制。
> 不过这是单次运行——按 τ-bench 的 pass^k 标准，多次全过的概率会低不少。"
