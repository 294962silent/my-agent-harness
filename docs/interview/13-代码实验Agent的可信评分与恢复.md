# 代码实验 Agent：可信评分、预算与恢复

2026-11-14。场景为本机 CPU 表格回归代码实验；不是官方长程 benchmark 成绩。具体结果与最终交付状态以[实施账本](../plans/2026-11-14-research-agent-runtime.md)和统一实验记录为准。

## P61：为什么已有 Agent 循环，还要增加场景层？

上一轮真实 HumanEval 校准的训练节点和可用测试可见分数饱和，优化器选择 baseline，C 与 B 的参数相同。没有可识别的学习干预，就不能靠修改项目名称得到“自进化提升”。新场景让 Agent 连续修改训练脚本，以独立重算的 RMSE 区分有效方案，并显式保留阶段、父子关系、预算和最终产物。

场景层连接已有 CodingAgent/Session/分支与评分，内核继续负责工具、上下文和调用。借鉴 AIDE 的 draft/debug/improve 实验树及 autoresearch 的固定代码/固定测量边界。没有迁移整个框架，也没有照搬上游效果数字。

深挖：连续 reward 只是提供更多比较信号，不能保证策略会学到有用规律。需要不同任务的策略 train/holdout/test；单数据集的 train/dev/final 是另一层划分。若只调几个数，固定脚本或随机搜索也是应有基线；LLM 的价值要在代码适配、修复和跨轮经验复用上独立验证。

## P62：如何避免 Agent 自己宣布“实验成功”？

原退出码评分只能判断命令是否成功退出；stdout 里的 RMSE 是候选程序可控制的文本。现在候选只输出 `id,prediction`，宿主要求 ID 精确一致、无重复、无缺失、预测有限，再从宿主标签重算 RMSE 与 `1/(1+rmse)`。非法结果为 unavailable，不补成零分或满分。

Agent 只有工作区文件工具；数据只在评分容器中出现。容器挂载训练集与预测特征，不挂载 dev/final 标签；代码和输入只读，唯一宿主可写挂载是一份有大小上限的预测文件。禁止把候选 pickle 加载进宿主，也不把提示词要求当作标签隔离。

深挖：把整个输出目录挂为可写，事后删掉多余文件仍无法避免运行中写满宿主磁盘，所以采用单文件写挂载、fsize 与资源限制。固定镜像 ID、脚本/数据/评分器 hash 防止一次实验中环境悄悄变化。Docker 依赖共享内核，不据此宣称完备攻击隔离；CLI/daemon 仍是可信基础。

## P63：为什么恢复不能直接重跑上次调用？

请求发出后进程中断，服务端可能已经执行和计费。只有开始记录而没有可信结算时，自动重试可能重复花钱；从配置重新建立预算则会绕过总额度。场景 ledger 在调用和评分之前预留，之后结算真实结果；恢复时从完整 journal 重建预算，不从零开始。

检查点只在完整 round 提交后形成，绑定脚本、报告、数据、策略、记忆快照和实现版本。新进程可以从这个边界继续；存在在途请求/评分/round 时阻断，保留不确定费用，要求调查，不能把它改成完成。

深挖：hash chain 能发现不完整尾记录和普通误改，但没有外部可信锚点，不能发现整条合法尾事件被删除，也不是防篡改签名。文件 fsync/原子替换与进程锁解决落盘和并发问题，但不能原子提交跨文件系统、Docker 和远程 API。Windows 上没有本实现对应的目录 fsync，边界需要如实说明。这里提供完成边界恢复，不声称任意时刻 exactly-once。

## P64：为什么 Mem0、Langfuse、RSI 不能都叫“优化器”？

Mem0 提供经验候选召回，正文、来源和有效性由本地存储复核；Langfuse 记录运行过程和用量，不能单靠安装它提升任务质量；Dream-RSI 调整有限的探索参数，必须通过独立验证才能发布。任务进度、预算和分数仍由宿主确定性状态负责。

正式对照中经验只从策略 train 写入，holdout/test 使用同一冻结快照。final 分数不回流选参或记忆。Mem0 与词法要以证据块召回、重复错误及端到端质量比较；云上传与本地 SDK trace 也需要分开验证。

深挖：本轮新增入口与工程测试不等于三项效果消融。参数搜索去重必须根据 train 中实际执行路径和预算，而非仅看参数字符串；不能观察 holdout 后重选。随机候选搜索顺序也不等同随机 Agent 行动策略。baseline 可以胜出，负结果也是有用证据。

## P65：为什么“每轮选最高分”仍可能退化？

审查发现旧 RsiRuntime 的 selected 只覆盖 Agent 生成的候选，baseline 虽然已经评分，却不在选优集合里。即使候选中最高分低于输入脚本，也可能导出更差脚本。研究场景必须把本轮输入基线一起比较；相同分数保留原脚本，只有严格更好的候选替换它。

场景层可以保留原有 runtime 的二元任务兼容性，在提交 checkpoint 时记录选择来自 baseline 还是 Agent、原 Agent 候选和分数、实际保留代码 hash，再让下一轮从实际选中脚本继续。trace 保留真实分支，不通过改写节点分数制造单调收益。修复状态以最终验收记录为准。

深挖：dev best 单调只是“按同一个开发集保留历史最好”的工程性质，不代表 final 一定提高，也不等于搜索策略优越。重复观察 dev 会过拟合；因此 final 一次性密封，策略还需要跨任务 holdout。对照组也应具备基线保留，不能把通用正确性修复当作 RSI 独有优势。

## P66：为什么真实恢复成功，RSI训练数据仍不合格？

本次真实v2两轮各运行三个候选，每轮两个在4次迭代后触发budget_exhausted，一个正常end_turn。完整round检查点能保留baseline并安全恢复，但导出训练树另要求候选终态完整；两轮trace均为None，不能把部分可见评分拼成“完整独立验证”。

这里有三个不同判断：候选程序是否产生可评分预测、Agent是否正常交付、整棵策略训练树是否完整。只检查其中一个就宣称全部完成，会掩盖预算校准失败。最终均值基线RMSE0.7554只证明密封final执行成功，不代表Agent或RSI提升。

下一批应先在新的策略train任务校准每候选所需迭代，明确文件工具与宿主评分的分工，再冻结总请求/token/时间预算做对照。所有策略共享动作和上限，不只给RSI更多机会；正式holdout/test不用于反复校准。单纯加轮次可能增加费用，必须衡量正常交付率与达到质量门槛的成本。此项是后续实验建议，不是本次已修复或已证实收益。
