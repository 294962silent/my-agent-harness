# 第二部分：四个核心实验（含完整方法与结果）

## 2.1 实验一：运行时自愈 A/B（转录本修复的价值）

### 要回答的问题

Agent 崩溃、Ctrl+C、进程被杀后，会话历史会留下**不合法的转录本**：
断头的工具调用（有 call 没 result）、孤儿结果（有 result 没 call）、空失败轮。

下一次请求时，主流 provider 直接返回 **400**，用户看到「一句话都发不出去」。

**这个自愈机制到底值多少？**

### 实验设计

| 环节 | 做法 | 文件 |
| --- | --- | --- |
| 故障注入 | 直接向 Session 写入 **32 例脏历史** + **8 例干净对照** | `scenarios.py` |
| 严格 provider | 假 provider 按 OpenAI tool-call 契约校验，不合法即抛 400 | `strict_provider.py` |
| 对照组 v0 | 把 `clean_provider_context` 在两处调用点替换为直通 | `run_ab.py` |
| 实验组 v1 | 完整运行时 | 同上 |
| **主指标** | **会话可继续率**：脏历史下再发一句话，能否被接受并正常 `end_turn` |
| 副指标 | 修复动作条数（+补齐 / -剥离），检查是否误伤干净历史 |

**关键设计**：不调用真实模型、不产生费用，**结果完全确定可复现**。

### 实测结果（2026-11-07 重新跑一遍确认）

| --- | --- | --- | --- | --- |

| 孤儿结果 | 8 | 0/8 (0.0%) | **8/8 (100.0%)** | -1.0 条 / 8 例触发 |

### 一处数据矛盾（已核实并判定）

`official_pi_progress.json` 文件头写 `passed_count=74`，
但逐条 `tasks` 统计是 **72 PASSED / 17 FAILED**。

**判定**：文件头 74 是过期值（可能是中断后重跑未更新），**逐条统计的 72 为准**。
简历写 72/89 是正确的。

### 关于 cache 指标的重要澄清

`cache_read_tokens` 累计 82,273,152 > `tokens` 41,737,271（**197%**）。

**这不是错误**。`cache_read` 是**累计读取量**（多轮对话中同一前缀被反复读取），
`tokens` 是**输入 token 量**。

**正确的命中率公式**：
```
命中率 = cache_read / (cache_read + 未命中输入 token)
```

> ⚠️ 简历若写「KV cache 命中率 66.3%」，必须能说清分母口径。
> 当前从该文件**无法直接反推**，需重跑实验或查原始日志。

## 3.2 三个最值得讲的缺陷（完整因果链）

### P0-1：权限门禁空转 ⭐ 最有价值的案例

**现象**：TUI 里弹出审批对话框，用户点「拒绝」，然后——文件还是被写了。

**根因链**（三层）：

1. `PermissionGate` 实现了，但**没有接进生产执行路径**
2. TUI 的确认回调是异步的，内核侧按同步调用处理，**返回值被丢弃**
3. 默认 fallback 是 **fail-open**：没有回调时默认放行

**为什么这个 bug 最危险**：它不是崩溃，是**静默失效**。
用户以为自己在控制，实际上没有。

**修复**：

```python
# src/my_coding_agent/permissions.py:5-6
# - fail-closed：非 autonomous 模式下，没有 confirm_callback 一律返回 block；
#   需要放行的嵌入方必须显式传 allow_without_callback=True
```

```python
# permissions.py:315-318
            if self.allow_without_callback:
                ...
            # 否则 block=True
```

**验证方式**（端到端，不是单测）：

| 路径 | 预期 | 实测 |
| --- | --- | --- |
| 批准 | 文件落盘 | ✅ 文件存在 |
| 拒绝 | `Tool 'write' blocked` | ✅ 报错 + **文件不存在** |

**关键**：拒绝路径必须验证「文件真的没写」，只验证报错信息是不够的。

**教训**：安全机制必须**默认拒绝**（fail-closed），
默认放行（fail-open）在「忘记传参数」时会静默失效。

---

### P0-2：API Key 泄漏到子进程 ⭐ 安全链分析

**现象**：用户在 TUI 里 `/login` 后，Agent 用 `bash` 跑的任何命令
（包括模型自己写的脚本）都能读到 API Key。

**根因**：`/login` 把 key 写进了 `os.environ`，子进程默认继承全部环境变量。

**这条的隐蔽性**：符合所有人直觉的「设置环境变量」，但 Agent 场景下
**子进程是模型控制的**，等于把密钥交给了模型。

**修复**（两层）：

1. 删除写入 `os.environ` 的那行
2. **子进程 env 白名单**（`src/my_agent_core/env_filter.py`）——
   只传白名单内的变量，其余全部剥离

**验证**：单测覆盖，检查子进程 `env` 里不含 `*_API_KEY`。

**教训**：Agent 场景下，**任何提供给模型的能力都可能被用来读密钥**。
环境变量是常见的泄漏面。

---

### P1-2：会话文件全量重写

**现象**：长会话下每产生一条消息，整个会话文件被重写一遍，还带 `fsync`。

**后果**：

- 10 MB 会话文件 × 每条消息 = O(n²) 写入
- 机械盘上肉眼可见的卡顿
- `fsync` 每消息一次，SSD 寿命受损

**修复**：增量追加（format v2）+ 指针记录当前分支位置 + `to_thread` 异步落盘。

**为什么之前是全量重写**：因为会话是**树状**的，分支切换需要「重写整个文件到某分支」。
新方案用指针记录当前位置，追加即可。

**教训**：树状存储 + append-only 日志 是兼容的，
关键是**不要为切换分支重写文件**，只移动指针。

# 第四部分：闭环流程（我是怎么做的）

## 4.1 单次开发的闭环

```
需求
  ↓
[1] 设计对比：至少找 2 个参考实现，写下选择理由
  ↓
[2] 写测试：先写失败测试（预期行为）
  ↓
[3] 实现：最小可行，不加额外功能
  ↓
[4] 跑测试：956 项全绿才算完
  ↓
[5] 端到端验证：真实场景跑一遍（不是只跑单测）
  ↓
[6] 记录：文档里写下「为什么这么设计」+ 遇到的坑
```

## 4.2 发现问题的三条路径

| 路径 | 例子 | 占比（估计） |
| --- | --- | --- |
| **真实使用** | P1-4 孤儿进程、P1-6 TUI 卡死 | 最多 |
| **外部评审** | P0-1 门禁空转、P0-2 key 泄漏 | 质量最高 |
| **写测试时** | P1-3 超时后线程仍在写 | 中等 |

**最深刻的教训**：**最危险的 bug 不是崩溃，是静默失效**。
P0-1（拒绝不生效）和 P1-1（usage 恒为 0）都属于这一类——
系统「正常工作」，只是结果是错的。

## 4.3 外部评审的价值（值得单独说）

`PROJECT_REVIEW.md` 这份评审报告发现了 3 个 P0 + 7 个 P1，
其中 **P0-1 和 P0-2 自己完全没意识到**。

**为什么自己发现不了**：

- P0-1：单测里 `PermissionGate` 逻辑是对的，只是**没接进主链路**
  （单测测了「门禁函数」，没测「门禁是否生效」）
- P0-2：符合直觉的「设环境变量」写法，需要**攻击者视角**才能发现问题

**方法论启示**：
单测覆盖率不能保证系统正确，需要**端到端的、带拒绝路径验证**的测试。
