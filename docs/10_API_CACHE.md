# 真实 API 实验：KV cache 命中率

> 目的：用**真实 API 调用**测量 KV cache 行为，回答悬了很久的「66.3% 命中率口径不明」问题。
>
> 数据源：`experiments/per_module/results.json`（`API-*` 记录）
> 复现：`uv run python -m experiments.per_module.exp_api_cache`
>
> 采集时间：2026-11-07
> 模型：`glm-5.3-flash`（经 opencode go 网关）
> 端点：`https://opencode.ai/inference/go/openai/v1`

---

## 0. 三个重要发现（先说结论）

### ① 命中率的正确公式（解开 66.3% 之谜）

**provider 返回的字段含义**（实测标定）：

```
prompt_tokens = 3490
tokens.input  = 1314    ← 未命中的部分
tokens.cache_read = 2176 ← 命中的部分
1314 + 2176 = 3490  ✅ 验证
```

**正确公式**：

```
cache 命中率 = cache_read / prompt_tokens
```

**而不是** `cache_read / tokens.input`。

**这解释了为什么早期算出 525% 的荒谬值**——分母用了「未命中部分」。

**对简历的指导**：
> "KV cache 命中率 66.3%" 必须说明分母是 `prompt_tokens`。
> 如果当时用的是别的口径（比如 `cache_read / input`），数字会完全不同。

### ② provider 端缓存跨 session 共享

实验中每次请求都用**新的 `x-opencode-session`**，
但相同内容仍然命中缓存（90.1%）。

**含义**：缓存键是**内容前缀**，不是 session id。
这对 Agent 设计有直接指导：**只要 prefix 稳定，新会话也能复用缓存**。

### ③ 缓存有最小长度阈值

| prompt 长度 | 是否命中 |
| --- | --- |
| 617 token | ❌ **0%** |
| 2,416 token | ✅ 90.1% |
| 4,487 token | ✅ 97.0% |

**推测阈值在 1000–2000 token 之间**（未精确测定）。
**实践含义**：短对话的 cache 优化没有意义，只有长上下文才值得。

## 1. 实验 API-1：冷启动 vs 重复请求

**假设**：全新内容首次请求无缓存，重复请求应高命中。

**方法**：用随机 UUID 构造全新前缀（约 2400 token），
连续请求 4 次，**每次换新 session**。

| 请求 | prompt_tokens | cache_read | 命中率 |
| --- | --- | --- | --- |
| 第 1 次（冷启动） | 2,416 | **0** | **0.0%** |
| 第 2 次 | 2,416 | 2,176 | **90.1%** |
| 第 3 次 | 2,416 | 2,176 | 90.1% |
| 第 4 次 | 2,416 | 2,176 | 90.1% |

**结论**：✅ 冷启动确实 0%，重复请求稳定在 90.1%。

**剩余 9.9% 未命中**是最后那条 user 消息（`"只回答 OK"`），
它每次都不同，所以不命中。

**这也验证了「跨 session 共享」**：session 每次都换，缓存照样命中。

---

## 2. 实验 API-2：prefix 被破坏

**假设**：篡改历史中段会破坏 prefix，导致 cache 失效。

**方法**：
1. 建立缓存（长前缀）
2. 对照组：完全相同的请求
3. 实验组：改写历史中段一条消息

| 场景 | cache_read | 命中率 |
| --- | --- | --- |
| 相同请求 | **4,352** | **97.0%** |
| **篡改中段** | **3,264** | **83.1%** |
| 差值 | **-1,088** | **-13.9pp** |

**结论**：✅ 篡改中段后命中率显著下降。

**细看**：篡改位置在中间，所以**篡改点之前的部分仍命中**（3,264 token），
之后的全部失效（丢了 1,088 token）。

**这正好印证了 prefix cache 的语义**：
缓存是**从开头逐块**匹配的，一旦某块变了，后面全部失效。

**对设计的指导**：
- 要改历史，**改得越靠后越好**（前面还能命中）
- 我的三层压缩管线的「免费层」只改工具输出（位置分散但不动开头），
  比「摘要层」（替换整个前半段）对缓存友好得多

## 3. 实验 API-3：Append-Only vs 滑动窗口 ⭐ 核心实验

**假设**：Append-Only 的 cache 命中率显著高于滑动窗口。

**方法**：6 轮对话，每轮内容唯一（真实对话特征），独立 session。

| 轮次 | Append-Only 命中率 | 滑动窗口命中率 |
| --- | --- | --- |
| 1 | 0.0% | 0.0% |
| 2 | 61.3% | 61.2% |
| 3 | 46.0% | 45.9% |
| 4 | 73.5% | **0.0%** |
| 5 | 61.2% | **0.0%** |
| 6 | 78.7% | **0.0%** |
| **平均** | **53.5%** | **17.9%** |

| prompt 长度 | Append-Only | 滑动窗口 |
| --- | --- | --- |
| 第 1 轮 | 1,183 | 1,184 |
| 第 3 轮 | 2,367 | 2,371 |
| **第 4 轮** | **2,960**（增长） | **2,372**（固定） |
| 第 6 轮 | 4,147 | 2,372 |

**结论**：✅ **Append-Only 53.5% vs 滑动窗口 17.9%，差 35.6 个百分点。**

**关键现象**：滑动窗口从**第 4 轮起命中率归零**——
一旦开始丢弃最旧的消息，开头的 prefix 变了，**整个缓存全部失效**。

**这用真实 API 印证了本地模拟的结论**（实验 3-A）：

| 方法 | prefix 变更次数 | 保留率 | 真实 API 命中率 |
| --- | --- | --- | --- |
| 本地模拟（3-A） | 0 次 | 100% | — |
| **真实 API（API-3）** | — | — | **53.5%** |
| 本地模拟（3-A，滑动窗口） | 16 次 | 15.8% | — |
| **真实 API（API-3，滑动窗口）** | — | — | **17.9%** |

**两条独立路径得出同向结论**：滑动窗口的命中率约为 Append-Only 的 1/3。

## 4. 这些结果如何修正现有文档

### 4.1 解开「96.7% vs 66.3%」的矛盾

之前文档里的两个数字：

| 指标 | 数值 | 来源 | 现在怎么看 |
| --- | --- | --- | --- |
| **前缀不变性** | 96.7% | 作者博客 | prefix **字节**未变的比例（设计侧指标） |
| **KV cache 命中率** | 66.3% | 外部评审 | token 命中比例（provider 侧指标） |

**现在有了第三个参照点**：本次实测 **53.5%（Append-Only）/ 17.9%（滑动窗口）**。

**三个数字的关系**：
- 96.7% 是「我们的压缩没有改动 prefix」的比例（设计意图）
- 66.3% 是「实际有多少 token 命中了缓存」（运行时结果）
- 53.5% 是「6 轮短对话的实测值」（本次，样本更小）

**它们不矛盾**，因为：
1. 量的对象不同（字节 vs token）
2. 场景不同（长会话 vs 6 轮短对话）
3. **provider 端还有自己的缓存策略**（最小长度阈值、驱逐策略等）

### 4.2 简历该怎么写

**推荐表述**（有实测支撑）：

> "实测 KV cache 命中率：Append-Only 策略 53.5%，滑动窗口仅 17.9%
> （glm-5.3-flash，6 轮对话，opencode go 网关）。
> 定位到滑动窗口从第 4 轮起命中率归零——丢弃最旧消息会让整个 prefix 失效。"

**不要写**：
- ❌ "命中率 96.7%"（那是 prefix 不变性，不是命中率）
- ❌ "命中率 66.3%"（口径不明，且无法从现有数据反推）

### 4.3 新增的设计洞察

| 洞察 | 依据 | 对设计的指导 |
| --- | --- | --- |
| 缓存键是内容前缀，不是 session | API-1 | 跨会话也能复用缓存 |
| 最小长度阈值 ~1000-2000 token | API-1 对比 617 vs 2416 | 短对话不必优化缓存 |
| 改历史越靠后越好 | API-2（-1088 token） | 免费层优于摘要层 |
| 丢弃最旧消息 = 全缓存失效 | API-3（归零） | 滑动窗口是最差策略 |

## 5. 实验过程中踩的坑（如实记录）

| 坑 | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| **Cloudflare 1010** | HTTP 403 `error code: 1010` | urllib 默认 User-Agent 被拦 | 显式设 `User-Agent` |
| **MissingSessionID** | HTTP 400 | 缺 `x-opencode-session` 头 | 加 `x-opencode-session: <uuid>` |
| **模型不可用** | HTTP 400 "Model is unavailable" | 模型名不对（proj 内目录过期） | 从 `/models` 拉真实列表（30 个） |
| **命中率 525%** | 荒谬数值 | 分母用了 `tokens.input`（未命中部分） | 改用 `prompt_tokens` |
| **缓存恒为 0** | 短前缀测不出缓存 | prompt 617 token < 阈值 | 加大到 2400+ token |
| **滑动窗口反而更高** | 88.1% vs 82.8% | 未隔离 session，跨请求缓存串扰 | 每次独立 session |
| **滑动窗口不归零** | 窗口稳定后内容固定 | 每轮内容相同 → 窗口内容不变 | 每轮内容加唯一标记 |

**最后两个坑最有价值**：
一个实验如果「结果符合预期」，很可能是**实验设计有漏洞**。
必须主动构造「会让它失败」的场景。

## 6. 仍未测的

| 项 | 为什么没做 |
| --- | --- |
| 缓存最小阈值的精确值 | 需要二分探测（约 20 次调用） |
| 缓存 TTL / 驱逐策略 | 需要等待（5 分钟 / 1 小时） |
| 多 provider 对比 | 需要各家的 key |
| 真实长会话（50+ 轮） | 成本较高（每轮几千 token） |

`usage` 里有 `cache_write_5m` / `cache_write_1h` 字段，
说明 provider 支持 TTL 分级缓存。**这两项的实测需要长时间等待，本次未做。**
