# 01A｜事件是什么：跟着一次读文件操作理解

> 这一小节只解决一个问题：程序为什么要发出“我进行到哪一步了”的通知？
>
> 学完以后，能分清“实际做事”和“告诉别人事情进行到哪一步”。

## 1. 先从你使用 Agent 时看到的过程说起

假设你给 my-agent 发了一句话：

> 帮我读取 hello.py，告诉我这个文件会打印什么。

假设文件里只有一行：

```python
print("hello")
```

这个文件是教学例子，不要求你创建或运行。下面的界面文字也是示意，方便理解各部分职责；实际事件名称取自项目源码。

为了回答你，程序需要安排读取工具访问文件，把读到的内容交给模型，再让模型生成解释。

这些是实际工作。同时，你还希望屏幕告诉你：“正在处理读取请求”“读取已返回”“正在生成解释”。否则你只能等最后一句答案，中间不知道程序进行到了哪里。

**事件，就是程序把中间发生的事情告诉外面的方式。**

## 2. 把这件事拆成两个动作

### 动作一：真的读取文件

程序调用读取工具，拿到文件内容。这一步访问了文件系统，完成了实际工作。

可以想象成：

```text
内容 = 读取 hello.py
```

### 动作二：告诉其他功能，现在到了哪一步

例如告诉界面：“读取工具的处理已经返回。”

可以想象成：

```text
发出通知：读取工具已经返回，结果在这里
```

第二个动作帮助界面、日志等功能了解过程。读取工作本身仍由工具完成。

一个日常类比是外卖：厨师做饭是实际工作，“商家正在备餐”是进度通知。手机显示了进度，并不表示手机替厨师做了饭。

## 3. 回到项目里，只认识两个事件名

本节先用两个名字对应上面的过程。

### `ToolExecutionStart`：准备处理这次工具调用

拆开看：`Tool` 是工具，`Execution` 是执行过程，`Start` 是开始。

你可以先把它理解为：

> “程序开始处理 read 这次调用了。”

项目中的这个通知发生在工具预检阶段，后面还可能进行权限检查。因此它表达的是“进入处理流程”，单看这条通知还不能断言文件已被读取。

### `ToolExecutionEnd`：这次工具调用的处理结束了

它携带结果和错误标记。正常读文件时，结果可以包含读取到的内容；发生错误时，也要看结果和错误标记，才能知道它是否成功。

因此，“结束了”和“成功了”需要区分。例如：

```text
情况 A：处理结束，读取成功，拿到了文件内容。
情况 B：处理结束，读取失败，原因是文件不存在。
```

界面可以根据同一类结束通知，分别显示成功或失败。

## 4. 这些通知到底给谁看

假设程序发出一条通知：

```text
工具：read
状态：处理结束
结果：读取到的内容
是否出错：否
```

不同功能可以使用这份信息：

- **界面**可以把工具状态更新为完成。
- **日志功能**可以记录这次工具调用的结果。
- **统计功能**可以累计一次工具使用。

这里的“可以”表示这套接口能支持这些用途，并不意味着每个功能都已经默认安装或自动执行。

它们拿到同一条执行信息，却分别完成自己的工作。负责读取文件的代码不必逐个了解每一种界面、每一种日志格式。

## 5. 为什么值得把“做事”和“通知”分开

考虑一个具体变化：你原来在终端使用 Agent，后来希望加一个网页界面。

如果读取文件的代码直接操作终端组件，它就需要知道终端怎样显示“读取完成”。增加网页时，还要考虑怎样让这段执行代码服务网页。

采用统一通知以后，分工更清楚：

```text
工具完成读取
    ↓
程序产生“工具处理结束”的事件
    ↓
终端按自己的方式显示
网页也可以按自己的方式显示
```

后两种显示是接口能够支持的设计用途，不代表当前仓库已经提供了网页产品。

从设计角度看，这个选择的价值是：**执行部分负责完成任务，显示部分负责解释进度。** 两边通过约定好的通知内容连接。

它也有代价：大家必须约定通知叫什么、里面有哪些数据、什么时候发送。后面的小节再解释这些约定如何写成代码。

## 6. 再走一遍 hello.py 的例子

把实际工作与通知放在同一条时间线上：

1. 你提交请求：“读取 hello.py，解释输出。”
2. 模型提出 read 工具调用。
3. 程序发出 `ToolExecutionStart`：告诉外面，开始处理这次调用。
4. 在允许执行的情况下，读取工具真的打开文件，拿到内容。
5. 程序发出 `ToolExecutionEnd`：告诉外面，这次处理结束及其结果。
6. 文件内容作为工具结果消息进入对话，交给模型继续处理。
7. 模型根据内容解释：“这段代码会打印 hello。”

第 4 步是读取工作，第 3、5 步是过程通知，第 6 步则让模型拿到回答所需的信息。

这里还有一个容易混淆的地方：界面显示“读取完成”，并没有代替第 6 步。模型仍需要通过自己的消息输入拿到读取结果，才能据此解释代码。

## 7. 想三个小变化，就能检查自己是否理解

**变化一：没有界面监听这条通知。**

只要核心执行流程正常消费和推进，读取工具仍然能够工作。界面观察者的职责是显示过程。

**变化二：界面把文案从“读取完成”改成“文件已读取”。**

这是显示方式的变化，通常不必修改读取工具的业务逻辑。

**变化三：文件不存在。**

工具处理会得到错误结果。界面需要查看结束事件里的错误信息，再显示失败原因。因此，一条结束事件本身不等于成功证明。

## 8. 横向对比先看这一层意思（选读）

这些项目都需要把运行过程提供给外围功能，但组织方法不同。本节只把它们翻译成容易理解的话：

- **my-agent**：运行中发出统一类型的通知，界面和其他观察者接收。
- **Pi**：也有统一运行事件，并会等待相关监听器完成。
- **oh-my-pi**：也发运行事件，异步监听器的工作不必由主流程等待完成。
- **Hermes**：面向界面的回调和面向插件的流观察采用不同处理方式。
- **DeepSeek Harness**：有一类事件还负责形成会话历史记录，承担的工作更广。
- **OpenCode**：把实时接收进度和读取历史日志分开提供。

这一段只用于建立方向感。具体差异、源码证据及固定版本见[设计与源码对照文档](01-只读事件与执行观察设计.md)。当前还不需要同时掌握这些实现细节。
