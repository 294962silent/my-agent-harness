一、Agent 评估体系：为什么首选 Terminal-Bench 2.0？

在代码类 Coding Agent 的评测中，主要有两个方向：

评估维度

SWE-bench (Verified)

Terminal-Bench 2.0 (Harbor)

评测核心

纯 Python 代码仓库的 Bug 修复与 Issue 处理

真实 Linux 终端命令行的复杂工程与系统运维能力

交互媒介

代码检索、静态编辑、产出 
git diff
 补丁

全功能 Linux 终端（Bash、系统包管理、编译链、网络、文件等）

测试场景

定位特定函数/类缺陷，修改代码并通过回归测试

编译 Cython 扩展、排查端口冲突、内存泄漏分析、Git 分支变基、权限排查等

环境机制

依赖特定 Conda 环境与大型镜像层叠加（通常超过 100GB）

每个任务自包含独立的 Dockerfile 与环境配置

判定标准

执行隐藏测试补丁并运行 
pytest

在沙箱内执行 
test.sh
 判定系统最终状态（Exit Code 0/1）

Pi 原厂态度

Pi 作者认为其与日常命令行开发习惯有偏差

核心结论
：实际开发中，软件工程师有 60%~70% 的时间在终端里排错、装依赖、查日志、调系统。Terminal-Bench 2.0 重点考察 Agent 在真实命令行环境下的工程操作与排错能力（已被 ICLR 2026 收录）。

3. Harbor 的四大核心架构支柱

统一 Agent 抽象接口（
BaseAgent
）
：

原生支持常见 Agent（Claude Code、OpenHands、Codex CLI、Aider）；

接入时只需实现 
run()
 方法，同时支持宿主机编排与容器内运行两种模式。

多后端弹性沙箱环境（
BaseEnvironment
）
：

本地原生支持 Docker API；

云端支持 Daytona、Modal、E2B、GKE 等调度后端。

黑盒断言判定器（
Verifier
）
：

不依赖输出文本匹配，以沙箱内真实测试的退出状态码与 
reward.txt
 为准。

标准化轨迹存储（
ATIF - Agent Trajectory Interchange Format
）
：

完整记录每一步 Prompt、思考过程、工具调用与标准错误输出，为强化学习（RL）与监督微调（SFT）提供轨迹数据。

四、Terminal-Bench 2.0 评测的核心指标

运行一个批次的评测后，主要输出 4 个维度的量化数据：

解决率（Resolve Rate / Pass@1）
：

任务总数中 
reward == 1
 的比例。当前国际主流前沿模型的基准得分通常在 
25% ~ 55%
 之间。

耗时（Wall Time）
：

每个任务从启动到完成的实际物理耗时。

Token 与成本统计（Tokens & Cost）
：

input_tokens
、
output_tokens
；

cache_read_tokens
（检验 Prompt 静态前缀缓存命中的关键指标）；

平均单题推理成本（USD）。

工具调用健壮性（Tool Health & Self-Healing）
：

单任务平均工具调用轮数（Turns）；

工具执行出错后（如命令非零退出、正则匹配未命中），Agent 能否根据输出进行自我纠正。

2. 深度剖析：官方评测环境（云原生）vs 本地单机环境的客观鸿沟

为什么许多模型在官方榜单上自测能够跑出超高分数，而在本地环境往往跑不通？Harbor 官方和各前沿实验室是如何解决物理瓶颈的？

① 官方评测环境的“温室条件”

Harbor 的底层设计将沙箱执行层（Environment Provider）进行了高度模块化解耦：

官方定位
：官方在文档中明确指出，
--env docker
（本地 Docker）
“仅适用于开发者在本地进行极小规模的简单冒烟测试（Sanity Check）”
；

生产云沙箱
：官方大规模跑 Benchmark 或 RL 训练时，采用的是 
Daytona / E2B 微虚拟机
 或 
Modal 云原生无服务器容器（
--env modal
）
；

原生 GPU 绑定
：遇到涉及视觉大模型（如 
sam-cell-seg
）的复杂任务时，云端沙箱原生挂载 NVIDIA A10G/H100 GPU，3 秒即可完成 ViT 特征图推理，根本不存在 CPU 显存爆满问题；

独占硬件资源
：每个云端实例拥有独立的物理核心与 16GB~32GB 独占内存，不会与宿主系统抢占时钟，更没有虚拟磁盘交换（Swap Trashing）的困扰；

纯净海外网络
：沙箱处于海外 AWS/GCP 骨干网，访问 
astral.sh
、
github.com
、
deb.debian.org
 拥有百兆带宽直连，绝不会遭遇 GFW 丢包、502 拦截或 SSL 握手阻断。

② 本地 Windows 宿主所面临的地狱级挑战：九大实战工程暗坑与根治全景

在我们这套本地环境（Windows 11 x64 + WSL2 + 本地 Clash 代理 + 4 并发）下，我们亲历了并最终根治了整整 
9 大隐蔽工程暗坑
：

Docker 虚拟网桥 IP 地址池耗尽（31-Subnet Limit）
：

痛点
：Docker 默认地址池最多仅支持 31 个并发网络。批量执行到第 25 题后，残留僵尸网桥占满 IP 池，导致后续容器秒级崩溃抛出 
all predefined address pools have been fully subnetted
；

根治
：在调度器执行前后嵌入无感生命周期强清理钩子（
docker network prune -f
），保证网络池永久充沛。

Debian 官方源 Fastly CDN 502 拦截与明文 HTTP 阻断
：

痛点
：赛题容器默认使用 
http://deb.debian.org
（明文 80 端口），遭遇本地代理中间节点丢包与 502 错误，
apt-get
 退出码 100；

根治
：在 Harbor 
base.py
 底层执行前置流注入，自动将软件源重写为 
https://deb.debian.org
，配合 
-o Acquire::https::Verify-Peer=false
 达成秒级稳定下载。

2 秒光速秒装 Node.js（彻底告别 NVM 抓取失败）
：

痛点
：容器启动时依赖 NVM 从 GitHub 抓取脚本，国内网络偶发 SSL 协议 EOF 阻断，导致 Agent 启动阶段 0 Token 闪退；

八、评测实战核心疑问与避坑全景（Q&A 深度技术沉淀）

在搭建整套 Harbor 自动化基准评测、解决沙箱跨进程通信、调试大模型行为边界的过程中，涌现出了许多非常尖锐且直击本质的技术疑问。以下将这些核心问题逐一拆解复盘，作为后续开发与评测的避坑指南。

Q1：做评估时环境设置上遇到了什么坑？前面为什么根本跑不起来？后期如何解决的？

答
：在最初启动评测时，经历了一段典型的“完全跑不起来 ➔ 跑起来但频繁卡死 ➔ 最终自动化批量并发跑通”的排障过程。前期阻断运行的核心原因主要集中在三大维度：

Harbor BaseAgent 适配器契约不符（实例化直接 TypeError 崩溃）
：

现象
：一执行 
harbor run
，还没开始做题，Harbor 在加载 Agent 类的瞬间直接报错退出：
TypeError: __init__() got an unexpected keyword argument &#39;logs_dir&#39;
。

根因
：最初的 
MyPiAgent
 类没有按照 Harbor 的反射规范声明 
__init__(self, logs_dir=None, model_name=None, *args, **kwargs)
；同时把 
version
 写成了 
@property
 装饰器，而 Harbor 规范要求 
def version(self) -> str | None:
 必须是实例方法。

解决
：重构 
__init__
 与 
version
，并在启动脚本中显式向子进程注入模块搜索路径 
env["PYTHONPATH"] = f"&#123;REPO_ROOT / &#39;src&#39;&#125;;&#123;REPO_ROOT / &#39;my-pi-eval&#39; / &#39;src&#39;&#125;"
，解决动态导入问题。

沙箱环境接口猜错（
env.read_file
 根本不存在，首个工具调用直接崩溃）
：

现象
：Agent 被实例化后，收到指令尝试调 
read
 工具，立即抛出 
AttributeError: &#39;DockerEnvironment&#39; object has no attribute &#39;read_file&#39;
，解题当场夭折。

根因
：误以为 Harbor 容器环境提供了高级文件读写方法，但 Docker 容器环境底层只暴露了唯一的命令执行通道 
await environment.exec(command)
。

解决
：在 Commit 
1cb75b0
 中彻底重构，放弃假想接口，全盘改用容器内原生 
cat
 读文件，用 Base64 管道写文件，彻底打通工具通道。

凭据隔离机制死锁（API Key 丢失与熔断）
：

现象
：启动报错 
ValueError: 评测环境未检测到 DEEPSEEK_API_KEY！评测模块严格禁止读取本地 ~/.my-pi-agent/auth.json
。

根因
：主项目规范禁止评测模块读取日常的 
auth.json
，而最开始仅依赖命令行环境变量，导致由脚本拉起的独立 Harbor 子进程未能继承父终端临时变量。

解决
：在 
my-pi-eval/
 下建立专属的 
.env
 隔离体系（
my-pi-eval/.env
，加入 
.gitignore
），让 
resolve_eval_llm
 优先加载评测专属 
.env
。

超大 Docker 镜像拉取在 Windows 下引发的进程死锁
：

现象
：89 道题中存在多个几 GB 的大镜像（如 
mteb-retrieve
 8.24GB），拉取时主线程卡死在

Windows 终端 GBK 编码崩溃与 CRLF 换行符破坏

现象
：Windows 终端默认代码页处理 Docker 输出的特殊 Unicode 字符时报

；向容器写入脚本带入 
\r\n

主项目

 定位是极简生产级内核，追求轻量发布。Harbor 拖家带口引入了

3. 为什么不能直接 
-v
 卷挂载（Volume Mount）到宿主机硬盘？

许多人的第一反应是：
“为什么不直接让 Docker 把容器内的 
/app
 目录用 
-v D:\code:/app
 挂载到 Windows 本地硬盘上，让 Agent 直接调本地 
open()
 读写？”

在基准测试（Terminal-Bench / SWE-bench）中，
严禁卷挂载
，因为这会导致评测断言全盘崩溃：

Linux 文件权限位全部丢失
：Terminal-Bench 大量考题涉及 Linux 权限管理（如 
chmod 755
、
chown root:root
、可执行位）。一旦挂载到 Windows 的 NTFS 文件系统上，Linux 权限位全部失效，
sudo
 或后台守护进程直接报权限拒绝；

符号链接与 Socket 崩溃
：Linux 下的软链接（Symlink）与 Unix Domain Socket 在 Windows NTFS 上无法原生支持；

换行符二次污染
：宿主机读写容易意外触发 Windows CRLF 换行符重写，破坏 Linux Shell 脚本。

因此，测试容器必须保持自己纯净独立的 Linux Overlay2 文件系统，宿主机绝不能粗暴地通过目录映射去破坏它。

4. 为什么写文件一定要依靠 Base64？（四大致命地雷与开箱时空闭环）

很多人的第一反应是：
“修改文件用 
echo &#39;code&#39; > file
 或者 
cat << &#39;EOF&#39; > file
 不是很直接吗？为什么非要绕一道 Base64 编码？”

因为直接用字符串写代码，本质上是
让你的代码在 Linux Shell 解释器面前“裸奔”
！代码里的特殊字符会直接撞上 Shell 语法分析器的枪口，触发 
4 颗毁灭级地雷
：

① 地雷 1：引号冲突（Quote Hell）导致语法当场炸裂

代码里必然充斥着单引号和双引号（如 
print(&#39;hello, "world"&#39;)
）。

外层包双引号
：
echo "print("hello")" > file.py
 ➔ Shell 看到第 2 个双引号即判定字符串提前闭合，后面的括号变成非法指令，报 
Syntax error: unexpected "("
；

外层包单引号
：
echo &#39;d = &#123;&#39;a&#39;: 1&#125;&#39; > file.py
 ➔ 
Linux Shell 存在一条绝对铁律：单引号内部无法转义单引号！
（哪怕写 
\&#39;
 也无效），命令当场崩溃。

② 地雷 2：
$
 环境变量被 Shell“自作聪明”地吃掉（Parameter Expansion）

大模型写的代码极常包含 
$
 符号（例如 Shell 脚本、PHP、Makefile、或正则表达式 
r"^\d+$"
）。

如果直接写 
echo "echo $USER, PID: $$" > run.sh
，
Linux Shell 会在写入之前，偷偷对它进行求值替换
！

$$USER
被替换成了当前容器用户
root
，
$$$ 被替换成了临时进程号；未定义的变量直接被替换为空字符串！

大模型精心写的代码，
还没写进文件，变量名就已经被 Shell 偷偷删光了
。

③ 地雷 3：反引号与命令替换（把代码当成真命令给执行了！）

如果代码中包含反引号 
`cmd` 
 或 
$(command)
：

直接作为 Shell 参数传递，Shell 会误以为这是给它的系统指令，
在写入文件的瞬间当场真的执行了它
，并将执行结果写进文件，甚至可能引发不可预料的系统破坏。

④ 地雷 4：为什么 
cat << &#39;EOF&#39;
 Here-Doc 语法同样靠不住？

有人会想用 
cat << &#39;EOF&#39; > file
，但它同样有致命暗坑：如果大模型写的代码里
恰好也定义了名为 
EOF
 的变量
（例如解析器常量 
EOF = -1
，或 Markdown 里出现了 EOF），Shell 会在读到代码里的那个 
EOF
 时
提前闭合
！后面剩下的几百行代码全被当成非法 Shell 命令执行，评测秒挂。

⑤ Base64 的降维打击：穿上“防爆装甲”

Base64 的数学原理是将任意二进制字节映射到 64 个极其安全的纯平 ASCII 字符集（
A-Z, a-z, 0-9, +, /, =
）。
在 Linux Shell 规则中，
这 64 个字符没有任何一个具备特殊语法含义（没有单双引号、没有 
$
、没有反斜杠、没有反引号，且被压成单行无换行）
！无论多么复杂的代码，穿上这层“防爆装甲”后，Shell 看到只是一堆人畜无害的普通字母，完全不触发解析直接放行。

⑥ 关键心智模型：是在哪进行 
base64 -d
 开箱？什么时候开箱？

很多工程师会困惑开箱的时空节点：

命令：
echo &#39;ZXhwb3J0...&#39; | base64 -d > /app/main.py

在哪开箱？（WHERE）
：

在 Docker 容器内部！由容器自己的 Linux 系统开箱。

宿主机（Windows Python）只负责在内存中打包；而任何 Linux 镜像（哪怕只有 5MB 的 Alpine Busybox）都 100% 内置 GNU 标准工具 
base64
，它在容器内负责开箱。

什么时候开箱？（WHEN）
：

就在容器执行这条管道命令的“那一瞬间”！

整个时间线是毫秒级、零临时文件的流式闭环：

1. 【宿主机打包】: Python 内存将代码 b64encode ➔ 发送管道命令给 Docker Exec；

Q11：上下文压缩机制是如何设计的？工具结果落盘何时触发？生成摘要是如何生成的？那次摘要请求本身能命中缓存吗？Pi 官方源码是如何处理这个细节的？

答
：上下文压缩与 Prompt Cache（KV-Cache）的关系，是整个 Agent 架构中最精妙、也最容易踩坑的领域。我们的设计以及 Pi 原厂的底层规范，可以系统拆解为以下 5 个核心技术环节：

1. 前提铁律：未达 80% 绝不动（彻底告别滚动裁剪占位符的缓存自杀）

早期踩坑复盘
：过去设计了“滚动滑动窗口”，每一轮把中间消息折叠为 
[snipped 15 messages]
，下一轮变成 
[snipped 16...]
。大模型服务端的 Radix Tree 前缀树在第 3 条消息处发生分叉断裂，导致分叉点后面的 
整整 8 万 Token 每一轮全部全价重算
！几十轮累加下来单题狂吞 1600 万 Token，直接触发 HTTP 402 欠费闪退，缓存命中率惨跌至 10%；

现在的绝对铁律
：
Append-Only 前缀不变性
。在未达到 80% 预算之前，历史消息连一个标点符号都不准碰，新消息只往末尾追加，稳稳锁死服务端 KV-Cache。

2. 工具结果落盘（L3 磁盘溢出）：什么时候触发？

触发时机
：
当且仅当上下文 Token 估算总量“突破 80% 动态预算阈值（
budget_threshold
）”的那一瞬间触发！

分级处理（免费层 Free Layer）
：

扫描所有 
role="tool"
 消息，只要单条输出超过 
20,000 字符
（约 5,000 Token）；

立即将其完整内容原样写入硬盘：
.my-pi-agent/tool-results/<tool_call_id>.txt
；

在发给模型的上下文视图中，替换为包含路径的精简预览（只留前 2000 字符）；

关键设计
：若大结果落盘后 Token 数降回了 80% 以内，
本次压缩立即结束，根本不需要花钱调用大模型生成摘要（L4）
！

3. 结构化摘要（L4 终极救生艇）：具体是如何生成的？

如果工具落盘后依然超过 80%，系统启动独立的大模型摘要流程（

4. 核心灵魂疑问：生成摘要本身也要发一次 LLM 请求，为什么不在原对话末尾直接追加“请总结”以复用原有的 8 万 Token 缓存？

这是一个非常高水平的第一性原理推演：
“既然服务端已经缓存了前几十轮的 8 万 Token，直接在末尾加一句‘请总结’，不就能白嫖这 8 万 Token 的缓存了吗？”

答案是：理论上确实能命中前缀，但工程上绝不能这么做！背后有两大工程权衡：

防止角色混乱与指令被劫持（Prompt Injection & Role Confusion）
：
如果直接在长对话末尾追加，前面的 System Prompt 是“你是一个 Coding Agent，请使用工具”，大模型在看到末尾时，极容易被上下文带偏，忍不住继续去发 
ToolCall
 调用 
bash
，或者被历史报错代码里的提示词攻击当场劫持。必须用独立的系统提示词将其定性为“纯数据总结助手”；

物理脱水（比命中缓存还便宜！）
：
原对话是一整套包含了几十页编译日志的 8 万 Token 庞然大物。直接发过去哪怕命中缓存，大模型注意力也会严重涣散，总结质量极其低下。
而通过 
_serialize_messages
，我们将工具输出截断到 2000 字符，把工具调用压缩到只剩函数名，
瞬间把 8 万 Token 垃圾日志脱水成了一段仅有 1.5 万 Token 的高纯度纯文本
！
就算没有命中原对话缓存，大模型也只需要计算这区区 1.5 万 Token，
总成本反而比让它硬吞 8 万 Token 还要便宜得多
，且摘要质量极高！

Q14：坦白局与局限性声明（真实复盘，绝不遮掩）：本次评测有哪些不够规范和严谨的地方？为什么没有全量重跑？

这也是我们第一次完整落地如此大规模（89 道题）、深水区的工业级沙箱基准评测。实事求是地复盘，本次评测客观上确实存在一些不规范和不够严谨的地方，坦白说明如下：

中断单题重跑
：

部分题目在早期因为本地虚拟化环境、网络或代理没配好，导致评测中途崩掉或闪退。针对这部分受基础设施偶发故障波及的任务，我们当时采取的是直接单题补跑，而非每一次事故都把全量 89 题推倒重来。

修改结构后未全量重跑（仅重跑失败任务）
：

早期我们曾因上下文压缩机制设计不当（逐轮滚动裁剪占位符导致缓存失效），在彻底重构 Harness 前缀不变性与工具调度流水线后，出于时间与经济成本考虑，我们只对之前失败的 Task 进行了重跑攻坚；此前在旧结构下已经满分通过的 Task 没有再去全量重跑验证。

Pi 官方缓存细分数据未做结构化记录
：

在抓取原厂 Pi 的运行日志时，外层统计脚本只提取了 
totalTokens
 与费用字段，未将原厂 Pi 底层记录的

为什么最终没有选择全盘推倒重跑？

现实成本极其高昂：赛题全集 89 题总镜像体积超过 120GB，部分单任务镜像（如 
mteb-retrieve
）动辄 20 多 GB，全量跑一轮需要数小时甚至十几个小时的高负载运转，并且消耗数千万级 API Token。出于个人开发者的实际预算考虑，实在无法支撑一次次全量推倒重来。

正视并公开这些局限性，是我们对待工程评测最起码的科学态度；同时也把这些真实踩坑经历沉淀下来，供每一位在本地搭建 Agent 评测沙箱的同行参考！
