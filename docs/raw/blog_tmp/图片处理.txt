Agent 中图片如何处理：从请求适配、资产溢出存储到上下文压缩的完整架构实战

在传统的 LLM 编码智能体（如早期的纯文本 ReAct 框架）中，Agent 处理的媒介几乎 100% 都是纯文本（源码、终端输出、Git Diff）。但随着 Agent 深入到 
Web 浏览、UI 自动化测试、数据图表生成、桌面运维
 等真实场景，
图片（视觉多模态）
 成了不可或缺的核心能力。

然而，将图片接入大模型 Harness（智能体运行宿主框架）远不止调用一次多模态 API 那么简单。图片数据拥有极其特殊的物理属性：
极高的 Base64 文本体积（一张 1080P 图约 2.6MB 字符）vs 相对较小的视觉语义 Token（约 1200 Tokens）
。

这种矛盾会贯穿图片的整个生命周期。一套成熟的多模态 Agent 框架，必须在三个关键阶段分别建立严密的防御关卡：

第一关（请求与交互层）
：如何图文混排？工具返回截图如何防止切碎？如何绕过 OpenAI 的协议限制？

第二关（持久化与存储层）
：如何避免数兆的 Base64 撑爆本地会话文件？

第三关（上下文与压缩层）
：长会话触达上下文预算时，图片如何估算、裁剪并兼顾大模型 KV-Cache 前缀缓存？

本文基于官方 Pi（
@earendil-works/pi-coding-agent
）及我们实现的 
my-pi-agent
 架构，全面拆解这三道关卡的工程实现与设计哲学。

1.2 图文交错的绝对保序（Interleaved Order Preservation）

在多模态交互中，
图文出现的相对顺序至关重要
。
例如人类给出的指令通常是：

“先看旧版界面：[截图1]，再看新版界面：[截图2]，请告诉我导航栏有什么改动？”

大模型依靠
自注意力机制（Self-Attention）与位置编码（Positional Embeddings）
在序列空间中建立语义联系：

1

[Text: "先看旧版界面:"] ──► [Vision Tokens: 截图1] ──► [Text: "再看新版界面:"] ──► [Vision Tokens: 截图2] ──► [Text: "有什么改动?"]

如果 Harness 粗暴地把文字集中在前面、图片集中在末尾，模型就无法判断哪句话对应哪张图。因此，

content
 列表中的块顺序必须与输入顺序完全一致（Source Order）
。

工序二：截断防护的类型分流（防止切碎 Base64）

Agent 框架在工具层通常配置有 
50KB / 2000 行
 的输出截断保护。

致命陷阱
：若对包含 Base64 的输出直接做字符串截断，Base64 会在某一字符处被腰斩。残缺的编码会导致模型 API 直接报 
HTTP 400 Invalid Base64
 崩溃。

解决方案
：在 
ToolResult.serialize()
 中实现类型分流：若输出为包含图片块的多模态列表，
完整保留结构体，坚决跳过文本截断
。

工序三：事件广播与消息实体解耦

广播给前端与 TUI 的 
ToolExecutionEnd.result
 仅包含纯文本说明；而进入底层 ReAct 消息历史的 
tool_msg.content
 则完整保留多模态数据。

工序四：资产溢出存储落盘

图片二进制写入本地资产目录

工序五：面向大模型的分发适配

针对 Claude 原生放入

第二篇：持久化与存储层（Session & Asset Spill）

4. 核心痛点：Base64 直存会话文件的三重灾难

Agent 的会话记录通常以追加式 JSONL（
.jsonl
）保存：

纯文本会话中，几十轮交互的 
.jsonl
 通常仅有 
30KB ~ 100KB
；

一旦引入图片，一张图的 Base64 就有 
2.6MB ~ 4MB
。15 轮带图交互会让文件体积膨胀至 
50MB ~ 80MB
。

直接写入 Base64 会带来严重后果：

原子保存磁盘 IO 卡顿
：每次追加消息执行 
fsync
 时，几十兆文件频繁同步，产生明显卡顿；

反序列化与内存 GC 压力
：加载会话时，
json.loads()
 反序列化巨型单行字符串会瞬时占用数百兆内存，引发 GC 停顿；

编辑器与 Git 瘫痪
：文本编辑器打开几十兆的 
.jsonl
 容易卡死，Git 追踪也失去意义。

第三篇：上下文管理与压缩层（Context Compaction & KV-Cache）

7. 多轮对话中的网络开销与 KV-Cache 命中机制

在多轮交互中，历史图片的数据流转存在两个关键事实：

7.1 未压缩前：每次请求必须将历史图片全量上传

大模型云端 API 本质上是
无状态（Stateless）
的。在上下文未触达压缩阈值前，底层水合机制会在每次请求时读取图片并生成完整 Base64 发往云端。

7.2 图片能命中 KV-Cache 吗？

能够命中，且收益极高，但非常脆弱。

缓存排布与收益
：

现代模型（Claude 3.7、GPT-4o）采用 Prompt Caching。在显存序列中，图片折算为视觉 Tokens（1080P 图约 1200~1600 Tokens）；

只要前缀保持完全一致，后续轮次中图片的视觉 Tokens 
无需重新经过视觉编码器计算
；

成本与延迟红利
：以 Anthropic 为例，缓存读取费用仅为常规输入的 
10%（享受 90% 巨额折扣）
，首字延迟（TTFT）大幅下降。

两大工程现实
：

服务端命中 Cache $\neq$ 客户端不用传网络字节
：缓存命中发生在云端 GPU 显存中，普通的无状态 API 依然要求客户端每次将 2.6MB 的 Base64 上传到云端网关。
它节省了模型算力和账单费用，但不节省上行带宽
；

字节级前缀脆弱性
：若历史消息变动一个字符，或工具重新读取时生成的 Base64 出现微小偏差，
整条前缀缓存直接击穿（Cache Miss）
，后续所有文字和上千个图片 Token 必须重新全额计费。

8.1 第一步：Token 启发式估算（1200 Token 权重）

痛点
：若按字符数估算（4字符=1Token），2.6MB 的 Base64 会被误算为 65 万 Token 导致频繁误触发压缩；若算作 0 Token，真实消耗又会撑爆窗口。

解法
：对标 Pi，硬编码单图等效字符 
IMAGE_EQUIVALENT_CHARS = 4800
（即固定 1200 Tokens）。计算消息规模时，显式排除 
data
 字符串，按图片块数量乘以 4800 累加，落在各大模型视觉 Token 的统计期望中心。

8.2 第二步：切分点回溯与活跃尾部（
retainedTail
）保护

系统从最新消息向前倒序扫描（
_find_cut
），累加文本与图片的等效字符；

累积达到 
keep_recent_tokens
（约 20,000 Token）处切分，对齐到用户轮次边界；

核心原则
：
retainedTail
 内的所有近期图片，
100% 完好无损保留其多模态 Block 与 Base64
，确保 Agent 正在执行的工作视力不中断。

8.4 深度洞察一：为什么摘要调用无法复用主会话的 KV-Cache？

System Prompt 分叉
：主会话是 Coding Agent 提示词，摘要调用是 Summarization 提示词。最长公共前缀在第 1 个 Token 就中断，
主会话显存里的 KV-Cache 0% 命中，全部按全额原价计费
；

消息形态重构
：多轮结构体被序列化为一段纯文本长字符串塞入模板；

模型异构
：主会话由高规格模型驱动，摘要通常分发给更敏捷便宜的小模型（如 Haiku / GPT-4o-mini），物理显卡不同，无法共享 Cache；

本质是“内存垃圾回收税（GC Tax）”
：这次调用不产出业务代码、无 Cache 优惠，必须追求极限低成本。Pi 通过
剥离 Base64（省数千视觉 Token）、剔除 Thinking 思考块、工具输出二次腰斩（限 2000 字符）
，确保以极小代价完成总结。

8.5 深度洞察二：摘要模型里到底有没有对图片进行描述？

有描述，但完全依靠围绕图片发生的文字对话提炼，绝不调用视觉模型去写“看图小作文”。

视觉模型写出的泛化看图描述在工程任务中充斥着噪声；

摘要小模型依靠
工具元数据
（
Read image file [image/png], 1920x1080
）和
人类与助手的业务对话
（“定位出 z-index 冲突并修改 CSS”），足以在摘要中总结出业务结论：

- 分析了用户提供的 1920x1080 界面截图，确认并修复了 z-index 遮挡登录按钮的问题
；

在软件工程中，
图片的价值在于看图后得出的结论与落实的代码修改
。结论沉淀在摘要中，旧图片的像素便可以功成身退。

8.6 第四步：上下文重组与前缀稳固

压缩后，向主模型发送的视图结构为：

1

[System Prompt] + [Compaction Summary 纯文本摘要] + [Epoch 截断边界] + [含最新图片的 retainedTail]

旧图 Base64 彻底蒸发，释放大量空间；同时静态摘要与系统提示词构成新的不可变前缀，开启下一个高命中率的 KV-Cache 周期。

8.7 进阶演进：图片墓碑机制（Tombstoning with Re-read）

若超长任务后续需要回溯久远截图，可在压缩时留下墓碑标签：

[Image Tombstone: file="dashboard_4k.png", 1920x1080, sha256="..."] (Base64 dropped. Use read("dashboard_4k.png") to re-inspect)
。
Agent 明确知晓过去存在此图，必要时可主动调用工具重新读取，兼顾预算与灵活性。
